# 架构不腐化：唯一来源、文档同步、棘轮与派发边界

与 [领域设计不跑偏](domain-guardrails.md) 配套。那篇讲规则住哪里；本文讲规则之外的东西怎样在几十个 PR、多个模型轮流实现之后仍然不散。来源是一个由 Agent 承担大部分实现的业务系统，项目细节已去掉。

腐化的典型路径不是大错，是一连串"顺手"：顺手在查询里补一条规则、顺手手改生成物、顺手更新基线让门禁过、顺手把文档改成和代码一致而不是反过来。每一步都有理由，加起来就是没人说得清规则在哪。下面四类手段各挡一类"顺手"。

## 一、唯一来源 + 生成 + 一致性检查

- **契约先行**：传输类型只有一份（OpenAPI），服务端与客户端类型由命令生成，CI 跑 `gen-check` 比对生成物与契约。手改生成物会红，契约改了没重新生成也会红。
- **一表一个拥有模块**：跨模块写只走拥有者的公开用例，缓存与投影从拥有者派生并有明确失效。import 方向由 depguard（Go）与 dependency-cruiser（TS）守，不靠约定；"packages 不反向依赖 apps""两端互不 import""呈现包不依赖 API 客户端"都是一条 lint。
- **命令只有一个入口**：所有检查、生成、迁移、启动从 `justfile` 进，CI 调同一入口；工具版本锁在 `mise.toml`。本地与 CI 跑的是同一条命令，"本地过了 CI 不过"的漂移基本消失。
- **抽象只解决已存在的重复或外部边界**：不预建通用 Repository、工作流引擎、多层转调。写进入口文档作为设计优先级，审查时拿来问。

## 二、文档与代码不许分叉

- **文档分层并有维护动作**：GitHub 状态（issue、PR）、Agent 入口直接点名的文档、经索引到达的现行文档、冻结快照与来源。每层写明"什么时候改、谁改"。
- **`docs-check` 进 CI**：死链（含相对链接与锚点）、用词基线、生成物一致性。搬走一个源码文件，引用它的审查报告链接立刻红——这次就抓到一次，修法是改成当时 commit 的 permalink，保留历史事实。
- **PR 模板三个必填**：对应领域文档哪一条、守护机制有没有变、影响了哪些文档。子线程发现实现与文档冲突时必须单列"与文档冲突"，不许自己改文档；父线程合并后补"实作注记"（日期、为什么偏离、现在以什么为准）。
- **ADR 带翻盘条件**：实现偏离 ADR 时改 ADR，不留着一份说谎的决策。决定里写清"选了／没选／为什么"，日后推翻有据。
- **决策只在一处**：业务决策与待决问题记在 issue 决策地图，答案只在子条目并附证据链接；范围（一期／二期）以功能清单的期别栏为准；分析层自提的功能一律二期。防止范围被"顺手"扩大。
- **术语表只放词条、定义、Avoid**：输出里出现术语表没有的概念，本身就是信号——要么在发明项目没有的语言，要么真有缺口。

## 三、棘轮：基线只能缩

- 同一原则用在四处：视觉差异清单、用词基线、既有问题清单、harness 落实清单。首次全量入库，之后只允许删行或等长替换，新增要在 PR 写理由并审查。
- Agent 最常见的腐化动作是"更新基线反映现状，让门禁通过"。任务里要明说不接受；棘轮把它从默认选项变成显式违规。
- 剩在清单里的每笔要写具体理由（种子差异、隐私投影、真实登录 vs 示范入口），不留"待修"字样；清单是日后审查依据，不是垃圾桶。
- 实现细节见 [TypeScript harness 第 3.5 节](harness/basic/typescript.md) 与 [code-review 棘轮](harness/code-review/dont-break-it.md)。

## 四、派发与合并的边界

- **任务模板写死**：先读、授权范围、不做、禁改路径、"自行引入的决定"必须单列、回复格式。子线程只开 PR 不合并。
- **父线程合并前固定核对，看 diff 不看回报**：merge-base 等于主干；禁改路径 diff 为零；自行引入的决定逐条接受或退回；抽查 handler 与查询有无业务 if；CI 全绿。子线程说"按文档做了"不是证据，这个项目至少五次是翻文档后退回的。
- **子线程停下来问的，父线程当场裁决并写进任务**：裁决本身是规则的一部分，下一个线程不该再问同一个问题。
- **测试放最低可观察层**：E2E 走真实 API，不允许数据库直写或认证旁路；门禁测试自己撞限速时，修测试基础设施（storageState 落盘重用），不改产品限速。
- **环境隔离**：每个 worktree 独立 Compose 项目名与端口，线程之间不互相污染；共享的本机测试环境不被子线程停掉或重新种子。
- **原型是规格不是代码**：呈现层抽共用包让正式两端与原型共用一份组件；需求靠文档链承载，灰色地带进文档不留原型；视觉门禁比原型骨架与正式基准。

## 五、升级过滤器

人只在三种情况被打扰：已写下的规则本身要变；要花钱或要人名下的帐号凭证；要送到客户面前。其余 Agent 按文档与变更分级自行裁决，事后列成"已决定，不同意再改"，不混进待决清单。

这不是效率手段，是防腐化手段：只有当文档真的能裁决大多数问题时，这个过滤器才成立；每一次"文档没答案所以问人"都是一条该补进文档的规则。

## 六、什么时候这些会失效

- 任一守护被降级为"建议"而非 CI 必过：等于没有。
- 父线程开始凭回报合并、不看 diff：子线程会学会怎样写回报。
- 棘轮清单允许"反映现状"式更新：门禁变成摆设。
- 文档与代码冲突时改文档迁就代码而不写注记：文档失去裁决资格，升级过滤器随之失效。
