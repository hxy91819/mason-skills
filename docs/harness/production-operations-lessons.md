# 生产运维 Harness：只读观察、有界重试与清理边界

长时间回归需要工具接续，但持久化、重试和清理都可能引入新的副作用。本文补充运行时运维经验；语言检查、测试分层和公共模块契约沿用本目录已有文档。

## 来源与阅读边界

经验来自项目 Z：一个跨地域供应云实例、由控制面调度任务的平台。
Agent 管家负责推进与裁决，实现线程承担编码、回归和运维取证。
这里合并同类事件，只保留可迁移的机制；原始工作簿、操作回执与私密材料不公开。
文中的做法包含事后提出的修复方向，不表示相关修复均已发布。
具体阈值须按负载、授权范围和恢复成本校准，不能直接当作其他项目的默认值。

## 1. 只读监视器也需要可靠生命周期

**现象**：临时后台进程退出后，没有人发现长回归已经完成或进入失败状态。
让 Agent 长时间留在回合里轮询，又消耗会话并拖慢人工交互。

**根因**：观察工作依赖临时终端，没有独立的进程托管与恢复入口。
任务执行、状态观察和通知被放进同一个易失会话。

**做法／判准**：长期 watcher 交给 systemd 等进程管理器，具备重启和状态查询能力。
明确只读接口范围，输出包含 production_actions=[]，表示本轮没有生产写操作。
该字段只是审计声明，仍需权限约束与调用记录支持，不能单独证明只读。
状态变化后唤醒执行线程，执行线程在人工等待处结束回合。

## 2. 状态文件必须可读且可追溯

**现象**：观察者写文件到一半中断，接手者读到不完整状态或把旧状态当成当前值。
输出包含用户或实例原始标识，也扩大了日志泄漏范围。

**根因**：状态更新不是原子的，记录没有区分采样时间、成功与读取错误。
为了排查方便保留了超出复盘必需的信息。

**做法／判准**：写临时文件、刷新内容后原子替换正式状态，按持久性要求同步目录。
输出采样时间、结果类别、稳定关联标记和错误状态，读失败不能覆盖成健康。
用户与实例只保留受控关联摘要；避免低熵标识的可枚举哈希，必要时使用带密钥摘要。
内部记录与公开报告分开，公开材料只描述机制，不复制关联标记。

## 3. 告警依据新信息与明确定义的比率

**现象**：同一个已知原因反复通知，淹没了首次出现的新故障。
只报失败数，又无法区分请求量上升和真实失败率恶化。

**根因**：没有按原因聚合、去重和设置观察窗口，分母也未定义。
通知通道承担了本应由本地事件记录保存的重复信息。

**做法／判准**：未知或新原因优先通知，已知原因本地累计并保持可追查。
结合窗口内次数与累计失败率，明确按请求还是实例计数。
新项目先校准窗口、阈值与最小样本数，不照抄一次发布的数字。
告警只推动调查；回滚决策与授权沿 [发布复盘](../agent-steward-production-rollout-lessons.md) 的边界处理。

## 4. 重试预算属于授权的一部分

**现象**：流水线失败后不断重试，额外构建与部署尝试悄悄超出原任务范围。
只留下最终响应，无法确定此前是否已经发生写入。

**根因**：次数、间隔和停止条件没有外显，也没有写操作前后的核销记录。
工具返回未知状态时，调用者把它当作“没有执行”。

**做法／判准**：按服务设置最大次数和最小间隔，执行前核对剩余额度。
每次保留意图、响应和读回三类内部回执，正文与密钥不进入公共材料。
响应不明先查询实际状态，不盲目重复写；配额耗尽停止并等新授权。
次数预算跨进程接续，不能通过重启脚本或换线程重新获得额度。

## 5. 构建重跑先区分工具故障与输入变化

**现象**：诊断包装入口缺模块搜索路径，测试还未进入业务就失败。
修好包装后重跑，与改了候选版本再跑，被混写成同一种验证。

**根因**：Harness 准备、业务断言、恢复清理没有独立结果。
重跑只追求绿色，没有说明它补的是哪段证据。

**做法／判准**：仅在工具自身问题已定位并修复时，按限定次数重跑原输入。
输入或版本变化、原因未知、同一步骤连续失败达到停止条件时，停下重新归因。
修复包装先做定向自检，不修改业务断言来消除故障。
原准备失败保留，补跑结果单列；诊断提前停止不记作完整业务通过。

## 6. 审批和合并脚本要绑定具体输入

**现象**：旧审批或旧授权文件仍指向冲突解决前的版本，脚本却准备继续合并。
平台列表短暂空缺又诱发重复提交写请求的风险。

**根因**：读取、审批和合并没有独立动作，授权没有约束目标版本与有效期。
写后核验只看请求成功，没有检查实际主干内容。

**做法／判准**：脚本分为读取、审批、合并三种动作，默认读取。
变更动作核对授权对象、版本、顺序、期限和允许的操作，输入改变即重新核对。
合并后读回合并状态、来源包含关系和目标文件差异。
详情查询用于核销最终状态；无法判定时停在未知，不自动再次合并。

## 7. 共享节点失败先看宿主机资源

**现象**：多个评测容器各起 MySQL，CI 只显示数据库没有运行。
重复重建容器仍失败，看起来像数据目录或镜像坏了。

**根因**：共享节点的异步 IO 配额耗尽，底层 io_setup 返回 EAGAIN。
容器级日志掩盖了宿主机共享内核限制，重试不会释放被其他任务占用的预算。

**做法／判准**：先保留数据库启动错误，再核对宿主机使用量、内核上限与并行容器数。
区分 IO 配额、内存、磁盘和数据目录错误，不凭笼统健康失败推定根因。
确需提高上限时按主机容量评估，通过持久化配置和读回验证生效。
同时限制并行度，避免把提高上限当作没有容量预算的永久解法。

## 8. 检出失败要核验对象完整性

**现象**：浅克隆 fetch 后仍无法切换到目标版本，重复构建失败在同一步。
平台返回的错误码没有说明缺失的是父对象。

**根因**：下载了引用并不等于拥有检出或比较所需的完整对象图。
重试原命令无法补齐固定深度之外的历史。

**做法／判准**：检查目标提交及所需父对象是否存在，再决定增加深度或取消浅克隆。
调整后验证可检出、可求共同祖先，候选输入仍与任务绑定。
修复对象完整性不能顺带换成最新主干来绕过错误。
把检出故障和业务测试失败分别统计，避免污染产品可靠性结论。

## 9. 多行参数经文件传递

**现象**：用文本截取工具拼接构建命令，标题或正文被截断，最终请求与任务不符。
终端展示正常，也不代表参数边界和换行被完整保留。

**根因**：把面向人看的多行输出当成稳定机器接口，叠加了 shell 插值风险。
命令构造和内容传递没有分离。

**做法／判准**：优先使用结构化字段，多行正文通过文件或带引用的 heredoc 传递。
使用工具支持的正文文件参数，避免对展示文本按固定分隔符截取。
发送前预览目标与正文；发送后回读元数据确认未截断。
不把令牌拼进命令回显，错误回执也不能输出敏感参数。

## 10. 工作区清理必须识别活跃使用者

**现象**：按临时文件年龄清理，删掉了仍在使用的 worktree 内文件，表现为大量文件缺失。
工具会话还记录旧路径，接续任务找不到工作目录。

**根因**：文件修改时间不是工作区空闲时间，进程、容器和工具引用都可能持续使用旧文件。
清理范围没有区分主检出、已合并分支与未交付状态。

**做法／判准**：空闲时长只作为初筛，同时核验进程、容器、工具锚点及 Git 操作状态。
先只读出计划；证据不完整就递延，主检出不纳入自动删除。
需要归档时先检查敏感文件并确认远端适合保存，再读回备份完整性后移除。
未获归档推送授权时保留本地；路径已丢失则核实原状态后重建同路径再接续。

## 11. 磁盘预算与删除边界一起设计

**现象**：共享构建机磁盘耗尽影响控制面，急于腾空间又可能扩大误删。
清理脚本变量为空或指向错误目录时，一次命令就越过任务边界。

**根因**：没有预留构建与恢复空间，清理工具也没有把所有权落实到路径。
只检查路径非空不足以证明路径确实属于本次执行。

**做法／判准**：持续监控容量，为清理设置单轮预算、保留策略、递延理由和可追溯记录。
递归删除只处理本次 mktemp 创建且身份再次核验的目录，参数同时使用非空保护。
受管 worktree 通过 Git 感知的移除流程处理，不能用通用目录删除代替。
未推送、未知引用、敏感忽略文件或活动状态不明时保留，并输出明确原因。

## 下次遇到同类问题时

工具应让接手者回答：看见了什么、是否写过、还能重试几次、恢复是否读回、哪些内容明确不能删。观察与操作的边界必须能从回执核验。
