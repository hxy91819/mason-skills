# 从原型复刻产品：错误从哪来，怎样用审查挡住

这份文档回答一个问题：把客户确认过的点击原型复刻成正式产品时，错在哪些地方、为什么三轮审查都没抓到、最后怎样的审查组合才有效。来源是项目 Y（轮廓见[原型到正式实现复盘](prototype-to-production-lessons.md)「来源项目」一节）一期功能完成前的最后两周：一次 94 项的功能设计对比发现 62 项差异，其中 7 项是「做错事」级别；之后七个修补 PR 的审查又抓到三类新错误。结论先说：

1. 原型是三层规格，不是一层。视觉、功能设计、领域规则各自需要一条审查线；只审视觉就会漏掉「功能存在但设计不一致」。
2. 审查要在每个 PR 合并前跑，而不是最后做一次大对比。最后一次大对比的产出是 62 项差异与两天的修补，成本远高于每个 PR 时顺手比一次。
3. 审查的产出必须是可核对的清单（编号、原型文件行号、正式文件行号、分级、建议修法），不是一段结论。清单才能派发、才能验收。

## 一、错误的来源分类

按项目 Y 实际发生的次序，错误分五类，每类有不同的审查方式：

| 类别 | 典型例子 | 为什么会发生 | 哪条审查线能抓 |
| --- | --- | --- | --- |
| 视觉差异 | 字号、间距、主按钮色、阶段标签色、区块顺序 | 子线程用自己的组件库习惯重写 | 结构骨架棘轮 + 像素基准（[复盘第九节](prototype-to-production-lessons.md#九视觉比对门禁)） |
| 功能设计差异 | 验收结果被预选；设备 CT 默认值从 3 只变成没有；施工人员要填内部 ID 而不是下拉选；只知道店名就找不到案场；手机端完全不渲染已回传的施工照片 | 实现者把「功能存在」当作「功能一致」；原型的输入方式、候选来源、默认值、条件显示、动作后导向没有被当成规格 | 功能设计对比（本文第二节） |
| 领域规则外溢 | 用例自己比角色决定是否计入；SQL 里硬编 bootstrap 账号 ID；用例用 `DeleteFunc` 过滤候选而不是让 identity 查询边界给出正确集合 | 查询投影类需求容易被当成「只是读」，绕过聚合 | 领域专项审查（[领域设计不跑偏](domain-guardrails.md)） |
| 双实现分裂 | 内存 repository 把上传者字段填成账号 ID，PostgreSQL 版填姓名 | 同套 repotest 没有断言该字段 | 领域专项审查的「双 repo 同套」核对 + 让子线程先失败再通过 |
| 基准漂移与误更新 | 相对日期让表格栏宽随当天变化；详情页照片误用查询页缩图容器，说明文字缩小换行变省略，顺带命中既有遮罩 | 像素比对失败时子线程的默认动作是「更新基准反映现状」或「加遮罩」 | 管家合并前逐张看基准差异（本文第四节） |

前四类是「做出来的东西不对」，第五类是「检查工具被改到看不见」。第五类最隐蔽，因为它让其他四类的审查失效。

## 二、功能设计对比：缺的那条审查线

项目 Y 之前做过两轮审查：一轮 UI 样式对比、一轮产品体验审查。两轮都通过了，用户进建单页却不知道电号和电脑编号的区别、只知道店名就找不到案场。回头看，两轮审查的范围写的是「视觉」与「体验」，没有一条审查写明要比「每个画面的互动与功能设计」。

补法是先在移转约定里加一行，把它定为规格：

> 每个画面的互动与功能设计：输入方式、搜索字段、候选来源、默认值、条件显示、校验、动作后导向、列表筛选、空状态 —— 属于功能规格，沿用；要改须在 PR 说明引用 ADR 或决策条目。「功能存在」不等于「功能设计一致」。

然后派一次全量对比，产出结构是：

- 按页面分区（建单与现勘准备、清单看板导览、详情与桌面阶段动作、手机各阶段、照片查询与主数据），每区一张表。
- 每行：编号、页面／功能、原型行为（引原型文件行号）、正式行为（引正式文件行号）、分级（P1 做错事／P2 缺功能或语义不同／P3 程序推导的差异）、证据截图、建议修法、是否需要契约改动。
- 一致的项也列，避免报告只有挑出来的缺陷。
- 单独一节「自行引入的判断」：审查者决定不列为差异的项，附依据（哪条 ADR、哪条裁决、哪条移转约定）。这一节让管家能快速核对审查者有没有把「已裁决的不同」误报，或把「未裁决的缩水」漏报。
- 最后一节「为什么前几份审查没抓到」。

分级标准要按使用情境定：P1 不是「改动大」，而是「用户在那个情境下会卡住或做错」。项目 Y 的 7 个 P1 里，F01 是「不知道完整电号就建不了单」，F42 是「不知道内部 ID 就派不了工」，改动都不大。

## 三、每个 PR 合并前的审查组合

项目 Y 最后稳定下来的组合是四层，每层解决一类错误，顺序固定：

1. **子线程自检与交付格式**。任务模板规定「先读」（原型文件、移转约定、领域模型对应节）、「授权范围」、「不做」、「自行引入的决定单列」、「回复格式」（逐编号：做了什么、验证方式、并排截图路径）。子线程交付前跑一次独立代码审查（项目 Y 用通用的 autoreview 技能），无 P0／P1 才开 PR。
2. **领域专项审查**。管家另派一个只读线程，三个固定问题：用例与 handler 有没有自己比角色／阶段／负责人；规则（资格判定、可见范围、候选集合）是否只在聚合一份；双 repository 是否同套测试。审查对象是分支 head，不等 rebase 完成，因为逻辑不受 rebase 影响。七个 PR 的审查抓到两处 P1（SQL 硬编账号 ID；用例内过滤候选），都是查询投影类需求绕过了聚合。
3. **管家合并前核对清单**（看 diff 不看回报）：CI 全绿；merge-base 等于 main；禁改路径（原型、ADR、术语表、领域模型、契约若未授权）零差异；known-diffs 只减行；抽查 handler／用例有没有新增业务 if；逐条看「自行引入的决定」；「与文件冲突」那段合并后由管家补实作注记。
4. **基准变化逐张看**（第四节）。

四层的分工：第一层让子线程把该做的做完，第二层挡规则外溢，第三层挡范围越界与棘轮松动，第四层挡检查工具被改坏。少任何一层都在项目 Y 实际漏过东西。

## 四、像素基准重产要逐张看

像素基准不是棘轮（允许更新），但大批重产会掩盖回归。项目 Y 的做法：

- 子线程 PR 里 `__screenshots__` 有大量 M 时，管家用脚本比旧新尺寸与差异 bbox：整页高度差 1～2px、差异从同一个 y 开始，通常是一个共同的小改动（多层面包屑加了一行）；某页矮 300px 就要问。
- 问法要具体：列高为何变矮，是少了一行内容还是样式改了，附旧新该区域未遮罩的实际截图；这次新增或扩大的遮罩选择器清单。项目 Y 这一问抓到详情页照片误用了查询页的缩图容器——所有自动检查都过了，只有人眼比对基准能看出来。
- CI 像素失败先看 artifact 的 diff 图，不是先重跑。表头栏位偏移几个像素等于被遮罩的内容变了（相对日期文字长度随当天变）；根因是时间，修法是固定种子时钟加浏览器 `page.clock`，不是加遮罩或重录。
- 子线程提议「更新基准反映现状」「加遮罩」一律拒绝，裁决写回任务；允许的只有「因 X 原因只更新受影响的 N 个状态并列出」。

## 五、要不要做成一个审查技能

建议做，但做成两件东西，不是一件：

**一份项目级的移转约定**（每个项目自己写，不通用）。里面写清楚原型的三层规格各自是什么、哪些是示范手段不搬（本地存储登录、前端授权、演示控制台）、哪些差异已经裁决。审查技能读它，而不是读聊天记录。

**一个通用的「原型对齐审查」技能**（跨项目复用）。输入是一组页面的原型文件与正式文件路径，加上项目的移转约定；输出是第二节那种结构的差异清单。技能正文要写死的东西：

- 比对维度清单：输入方式、搜索字段、候选来源、默认值、必填与校验、条件显示、动作后导向、列表筛选、空状态、权限下的可见范围。每个画面逐维度过，不比「整体感觉」。
- 分级标准按使用情境，P1 的定义是「用户会卡住或做错」。
- 一致的项也列；审查者自行决定不列的项单独成节附依据。
- 原型里的示范手段不算差异；哪些算示范手段由移转约定说，技能不自己判断。
- 输出引原型与正式文件的行号与并排截图，没有证据的差异不列。
- 技能只产清单不改代码；修补另派。

触发时机写在项目的 Agent 入口文档里：每个前端 PR 开出后、合并前，对 PR 触及的页面跑一次；不是最后做一次全量。全量对比保留给里程碑（原型确认后第一次完整复刻完成时）。

不建议把领域专项审查并进这个技能。两者读的东西不同（一个读原型与页面，一个读聚合与用例），合并后提示会太长，审查者容易只做熟悉的那半。

## 六、顺序与节奏上的教训

- 多个分支同时开 PR 且都碰契约与视觉 spec 时，合并要序列化：每条分支只在轮到时 rebase 一次、全套跑一次；其他分支先改好本机持有等信号。项目 Y 一轮全套约 40 分钟，并行 rebase 会让每条分支跑两到三次。
- 领域专项审查在 rebase 前就派；CI 在 rebase 后再看。
- 修补批次按页面分区派（建单、详情、清单、手机、主数据），每批一个 worktree 一个端口偏移；批次间重叠的文件（契约、生成物、视觉 spec、照片键）由后合并的分支解冲突，规则是「main 为准，两边新增的状态都保留」。
- 子线程停下来问的问题，管家当场裁决并写进任务；同一问题不让下一个线程再问。

## 七、技能试跑的校准记录（2026-10-18）

技能写好后在项目 Y 的三个页面群试跑三次，每次都改了技能：

1. 第一次（devin）：没做环境探针就读代码，20 分钟后以「无法访问测试站」交了统计全为 0 的报告。改：第 0 步探针，探针不过就停下报回，不交推导报告。
2. 第二次（devin）：探针「通过」但截的是登录表单；表格从旧报告抄结论、编了行号，声称正式版仍只接受完整电号，而线上 bundle 已是新版。改：探针图必须是登录后页面；每行描述必须能在该行引用的截图上看到；旧报告审完才读。派发方核对回报时先抽一张它引用的正式截图看，再决定信不信表格。需要真实浏览器操作的审查不派这家 provider。
3. 第三次（amp）：先卡在三个环境问题（前两次触发的登录限流、任务里密码位置写错、前次线程遗留的端口占用）并正确停下报回；清掉后 45 分钟交出 36 项（一致 16、差异 20），四个角色真实登录，每条差异配对截图并自检。它同时给出最有用的反馈：候选全量性与日期边界要派发方给数据集；页面 × 角色 × 阶段缺分母；单张终点图证明不了动态行为；「正式比原型多」的扩充没有分级位置；「缺任何一项不交」让部分覆盖的有效结果交不出去。这些都改进了技能（覆盖矩阵、扩充与已裁决两级、操作步骤、完整／部分两种交付）。

另一个校准发现：第三次把「多选下拉变核取方块」「整列点击变链接」列为 P2，而项目早先的审查已按「输入与结果相同就接受控件替换」裁决为一致。技能本身无法知道项目接受了什么，只能靠项目级移转约定写明已裁决的差异清单——这正是第五节说要两件东西而不是一件的原因。
