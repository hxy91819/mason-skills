# Agent 管家主导生产灰度：从候选回归到发布裁决

一次多周发布最容易失控的地方，是把线程完成、检查通过、合并成功和生产可用混成同一个状态。本文按这些状态之间的交接整理经验。

## 来源与阅读边界

经验来自项目 Z：一个跨地域供应云实例、由控制面调度任务的平台。
Agent 管家负责推进与裁决，实现线程承担编码、回归和运维取证。
这里合并同类事件，只保留可迁移的机制；原始工作簿、操作回执与私密材料不公开。
文中的做法包含事后提出的修复方向，不表示相关修复均已发布。
具体阈值须按负载、授权范围和恢复成本校准，不能直接当作其他项目的默认值。

## 1. 管家保留判断，任务交付必须可核验

**现象**：实现、排查和汇总都挤在管家会话里，主线推进与用户回应相互阻塞。
线程交回一个肯定的摘要，也可能藏着未验证的推断。

**根因**：执行工作占满上下文，编排者失去核对范围、归属和取舍的时间。
多转述一次就多一次信息损耗，不能把子线程的结论直接视为验收。

**做法／判准**：管家维护目标、授权边界和验收判据；实现线程交回证据与未覆盖项。
固定范围编码可按较低难度派发；运维、回归和凭据任务至少按中等难度处理。
现行分档以 `$bb-model-routing` 为准。
跨组件且归因不明时升级调查难度，先收事实再决定修法。
是否完成以交付物及读回为准，不能只依据线程结束。

## 2. 候选组合才是合并门禁的对象

**现象**：多个分支各自通过，合到主干后却无法说明最终组合是否被测过。
逐分支要求“等于候选”也会误报，因为每个分支只携带部分改动。

**根因**：验证对象和交付对象不一致，缺少组合级来源证明。
分支之间还有依赖、冲突解决与被其他分支携带的变更。

**做法／判准**：先生成候选控制面与候选实例镜像，在个人测试环境跑完整回归。
核对各变更按约定顺序叠加后的结果与候选一致，记录排除项。
逐个合并后回读主干，按文件内容与模式核对已测范围。
少合一项也会改变候选；必须重新说明差异对行为和门禁的影响。

## 3. CI 状态和实测结论分开交付

**现象**：代码托管平台显示全绿，但相关 CI 只做了目录或元数据检查。
修复后的代码又有变化，旧审查结论仍被沿用。

**根因**：检查名称被当成覆盖范围，审查意见没有绑定输入版本。
平台状态证明指定任务成功，不自动证明业务路径已执行。

**做法／判准**：每项变更同时交付 CI 结果、实测环境与覆盖边界、独立审查结论。
写清在哪种环境测过什么，以及什么未测、为何未测。
代码变化后重新判断审查与回归是否仍适用，不复制旧通过结论。
个人测试环境足以覆盖时即可推进；共享预发布只补无法在前者验证的差异。

## 4. 失败归因不能靠挑选绿色重跑

**现象**：同一候选既有成功又有失败，早期分别被猜成资源池缺货或某项变更新增。
进一步对照才发现，简单标签没有解释实际失败阶段。

**根因**：把时间相关当因果，把一次成功当作排除间歇缺陷的证据。
准备夹具失败、业务失败、恢复失败也被混入同一个结果。

**做法／判准**：先定位失败发生在哪一阶段，再按授权进行定向复现与旧制品对照。
多次重跑必须有固定输入、次数预算和明确问题；失败原件始终保留。
归因回执写时间线、代码路径、观察、推断和缺口。
旧版复现能支持“机制既有”，不能直接豁免本次门禁或证明频率未变。

## 5. 冲突解决也是候选变化

**现象**：前一项合并后，后一项从可合并变成冲突，旧审批仍留在平台上。
列表接口还可能短暂查不到刚合并的记录。

**根因**：合并顺序改变基底，审批与自动化授权可能仍绑定旧输入。
平台列表存在状态传播延迟，空列表不等于写操作失败。

**做法／判准**：解决冲突后核对整树差异，完成必要检查并刷新绑定新输入的授权。
按单项详情接口读回来源版本、合并状态和主干包含关系。
状态未知时先查询核销，不重复发送合并请求。
合并成功只证明代码进入主干，不代表构建、镜像发布或部署完成。

## 6. 门禁上线要处理存量与平台语义

**现象**：新模板要求一上线，大量历史变更都不符合；临时更改所有者配置也没换掉既有审阅人。
请求审批时才发现目标审阅人不在该变更的槽位里。

**根因**：新规则直接约束存量，且误以为平台配置修改会追溯更新已有记录。
模板、CI 校验与平台创建时固化的元数据属于不同层。

**做法／判准**：先对受控作者强制执行，对其他作者提示，再逐步扩大范围。
模板明确测试环境、测试内容和未测原因，CI 只核验能机械判断的字段。
创建变更时核对审阅人；确需重建时保留原讨论与追溯关系。
审批、合并分别验证端点语义，不能把批准响应当成合并回执。

## 7. 发布通道与主干内容一起核对

**现象**：手改部署配置看似快捷，却绕过正常晋级记录；并行工作又让主干包含其他人的未发布代码。
只盯着自己的差异，无法解释实际部署包带了什么。

**根因**：源码、发布输入与部署配置之间失去唯一晋级链。
团队并发是常态，个人任务边界并不是制品边界。

**做法／判准**：生产变更沿既定主干晋级通道执行，避免旁路手改 GitOps 配置。
合并前检查主干上的未发布内容，把并行变更纳入兼容性判断。
项目 Z 采用默认包含并行内容的约定；其他项目必须明确自己的发布集合政策。
新生产云资源纳入基础设施代码，密钥经受控加密流程维护。

## 8. 夜间窗口要在截止前进入稳态

**现象**：长回归与恢复取证接近夜间截止点，仍有继续合并或换池的冲动。
把“已经开始”理解成可以无限延长，最终没有稳定交接状态。

**根因**：截止规则没有与步骤耗时、恢复预算和待决问题一起规划。
停止写操作与停止只读取证是不同决定，不能混用。

**做法／判准**：为本项目约定禁止发布、合并与改池的夜间窗口，并提前留出恢复余量。
临近窗口仍有未知失败，就延期写操作，保存检查点与当前状态。
夜间只读监视及必要恢复另按既有授权判断，不从窗口规则推导权限。
交接必须说明运行中的任务、恢复是否完成以及下一次允许推进的条件。

## 9. 监视器告警不自动授予回滚权

**现象**：看到总体失败上升便回滚，后来发现信号不属于本次负责的路径。
误回滚既浪费时间，也增加了版本切换与恢复工作。

**根因**：监控范围、故障归属和操作权限没有分开。
观察到异常只能触发调查，不能自动建立当前变更的因果关系。

**做法／判准**：监视器只告警，回滚由有权限的人根据本次路径的信号裁决。
列清支持归属的证据、回滚目标、预期收益与恢复成本。
对明确不在当前责任范围的旁支问题记一行，不让发布任务不断扩张。
严重且阻塞主线的问题按项目规则升级，不能用范围约定忽略真实危险。

## 10. 工作簿存状态，要求账本存闭环

**现象**：跨会话后重复讨论旧决定，用户要求在长消息和线程摘要中消失。
把实时日志塞进工作簿，又让状态页越来越难读。

**根因**：可恢复状态与事件历史混在一起，没有稳定的要求追踪入口。
上下文压缩不会自动保留下一步所需的操作约定。

**做法／判准**：路线每阶段一行，标明进行中、排在何项后或等待用户。
决策写背景、建议、状态以及为什么必须由人决定；要求账本记摘要、采纳结果和出处。
用结构检查、路线对账与账本检查发现遗漏，压缩前写检查点。
原话只保留在私密账本；公开复盘转述做法，不复制内部引用和操作标识。

## 11. 沟通让人看见下一步与已发生动作

**现象**：长回复混写多个线程，用户分不清哪些是新待决、哪些已执行。
中途问题虽在进度里回答，最终交付消息却缺少答案。

**根因**：报告按工具调用顺序组织，缺少按任务和决策的归并。
编号不标类型，也让构建、部署和代码变更互相混淆。

**做法／判准**：结论先行，每个线程一个块，链接附一句具体说明，编号明确对象类型。
需要人定的部分只列新变化，给推荐及其理由。
最终回复重述中途问题的答案，并列出本轮实际生产动作。
等待人工时结束执行回合，由只读 watcher 在状态变化后唤醒，避免 Agent 空转轮询。
