# 从点击原型到正式实现：一次 Agent 主导开发的复盘

这份文档记录项目 Y 从客户确认原型走到正式后端、两端前端、部署工具的经验，供同类项目参考。它是复盘，不是技能；只保留可迁移的做法，项目原件、客户材料与业务规则留在项目仓库（其 ADR 与 Agent 入口文档）。原型本身怎么做、怎么让客户确认，见 [客户确认原型复盘](client-confirmation-prototype-lessons.md)。

## 来源项目（项目 Y）

本文经验来自一个私密项目，这里只保留与做法有关的轮廓，称为项目 Y：

- **业务**：B2B 多方协作的工单系统。一张工单在多家公司、多种角色之间按固定阶段流转，每个阶段有回报表单、附件与按角色不同的可见范围；一个客户、一期范围、二期预留外部系统对接。
- **后端**：单体 Go 服务 + PostgreSQL + S3 兼容对象存储。聚合导向的领域模型，单一限界上下文：规则只住聚合、用例只编排、读写分路、聚合根带版本；OpenAPI 契约生成两端类型。
- **前端**：桌面运营端（React 18 + antd）与移动现场端（React 18 + antd-mobile）两个应用，共用呈现层包与 API 客户端包；同栈点击原型先经客户确认，之后作为规格而非代码。
- **过程**：Agent 承担大部分实现与审查，人只裁决规则与范围；需求链是客户原始材料 → 决策记录 → 领域文档 → 编号测试；所有检查从单一命令入口进 CI；本机测试环境经单一网关对外。
- **规模与时点**：一期约三十个功能项、七个聚合、二十余个 PR；文档写于一期功能完成、客户验收前。

## 一、原型承载什么，不承载什么

原型做对了两件事：让客户用点击确认需求（十几轮回馈、十个 ADR 都靠它），以及给后端一份可执行的规格（状态机的每个 action 对应一个用例、前端的授权判断对应一条规则）。它没做到的是介面程序直接复用，而这不是能力问题，是我们把它定义成"规格不是代码"却用散文写规格。

结论是把原型拆成两条线分别承载：

| 线 | 真源 | 交接方式 | 守护 |
| --- | --- | --- | --- |
| UI 与版面 | 原型页面本身 | 把 token、呈现组件、页面骨架抽成共用包（`packages/ui`），原型与正式前端都 import；组件只收 props，不含授权与阶段规则 | dependency-cruiser 挡反向依赖；每个"页面 × 角色 × 状态"对原型截图做比对，超阈值 PR 红；派发模板强制附并排截图 |
| 需求与规则 | 文档链：客户原话（raw）→ 决策登记的裁决 → 功能清单期别、领域模型、ADR → 编号测试 | 正式实现只对文档链，不对原型 | 追溯脚本双向检查"文档条目有编号、代码有对应测试"；lint 挡规则写错位置 |

灰色地带是互动规格（表单有哪些栏位、步骤顺序、谁看哪个区块）。它们必须进领域模型与功能清单；审查发现某个行为只存在原型、文档没写时，先补文档再改程序，不去抄原型，否则原型重新变成真源，冻结后就没人维护。

教训：规格必须是可检查的东西。后端规格有编号、有测试、有追溯，所以三个不同模型实现都没漏；前端规格是一段"沿用页面结构与 token、组件重写"，三个模型各画各的，必漂。Agent 只做被量的事。

## 二、需求链怎么搭

- 原始材料只归档不改写；每条裁决一张 issue，关闭时必须附证据链接；文档与原型都必须和裁决一致，打架时没对上裁决的一方是 bug。
- 术语只在一个文件（词条、定义、避免用词）；结构性取舍进 ADR（三条件：难逆转、没背景会觉得奇怪、真有取舍）；一期二期范围只在功能清单的一栏，其他文件只引用。
- 没答的问题先按建议值做进原型并标"暂定"，请客户再确认一次；确认后才做后端设计。
- 领域模型的不变量、转换表、可见范围表给编号，编号冻结只追加；测试案例名带编号；脚本在 CI 里双向对照。
- 收到任何来源的需求，Agent 先做"领域影响评估"：名词动词是否已在术语表与转换表里，按小改（规则内容变）、中改（名词在动词不在、聚合边界要动）、大改（名词都不在）分级；中改以上停下来提醒人发起评审。

## 三、领域驱动的轻量版

展开版见 [领域设计不跑偏](domain-guardrails.md)。

对象是单个限界上下文的内部业务系统（状态机、多方可见范围、库存类不变量、低并发）。CRUD 后台、报表、短命项目、整合层、单一热点高并发不适用。

- 规则只住在聚合：转换表、可见范围、不变量各只有一份实现；聚合是纯内存对象，不 import repository、HTTP、其他模块。
- 用例只编排：载入聚合 → 调方法 → 同一事务保存 → 回投影；用例可以按聚合回答的问题分支，不得自己比阶段、角色、负责人栏位。一个用例一笔事务可跨多个聚合（单体单库）。
- 读写分路：写走聚合守不变量；读直接拼 DTO。放哪边的判准：两处算得不同算 bug 吗？算就是规则，不算就是呈现。
- 先内存后数据库：不变量测试不碰数据库；repository 接口先出内存版，同一套测试组再跑 PostgreSQL 版。
- 乐观版本号在 repository 统一做；命令路径载入聚合时另锁根列，避免多表拼装在 ReadCommitted 下读到不一致状态（曾出现间歇失败）；跨聚合唯一性由数据库约束兜底。
- 不用工厂、领域事件、CQRS 框架。

七项守护全部 CI 必过：不变量追溯、import 方向 lint、禁止位置 lint（handler 与查询用例不得比较阶段／角色／负责人）、双 repository 同套测试、需求变更固定路径（改文档那一条→测试红→聚合绿）、领域专项审查（三问：两处算不同算 bug 吗；这个用例载入几个聚合；有没有用例自己比栏位）、任何一项列为建议即视为未建立。

审查首次全量试跑的收获：零个"规则写错地方"，全部是"规则没写完整"或"测试挂错编号"。设计保证位置唯一，不保证齐全；齐全只能靠从文档推导的测试和审查。后来把审查发现的两类错（`CanAct` 与命令方法分裂、测试编号与断言不符）加进审查技能的固定核对项。

## 四、派发与合并流程

- 每个 PR 一个 worktree 一个分支，基于最新 main；子线程只开 PR 不合并。任务文本按模板写死"先读、开工前对齐远端、授权范围与不做、要做逐条可检查、自行引入的决定单列、交付与验证、回复格式"。
- 主工作区常有其他线程未提交改动，所有派发走 worktree；子线程遗留的 Compose 环境定期清理。
- 合并前固定核对：CI 全绿、merge-base 等于 main、禁改路径零差异、抽查聚合与 handler、逐条过"自行引入的决定"、文档冲突自己修或回给对方。后端 PR 先派独立审查线程再合并；前端 PR 核对基底与"后端只动投影"后直接合并。
- 子线程的"自行引入的决定"由编排者收，只有触到已写下的规则才上报；回报时列成"已决定，不同意再改"，不混进待决清单。
- provider 额度耗尽或连接错误：先保全未提交进度（WIP 提交），任务文本原样取回并附"接续说明"，沿 fallback 链改派；同一天某 provider 连续失败就直接从链上下一个起派。
- 编排者的记忆放工作簿（路线位置、从文档推不出的操作约定、只有人能做的待办），不放线程产物。

人只在三种情况决策：改动会变更已写下的规则；要花钱或要人名下的账号凭据；要送到客户面前。其余按文档裁决、事后回报。

## 五、测试放在最低可观察层

| 层 | 放什么 | 数量级 |
| --- | --- | --- |
| 聚合与用例（内存） | 每条转换、可见范围、不变量、全流程、并发抢同一资源 | 几百，毫秒 |
| Testcontainers | 拆装、约束、版本冲突、取号、迁移往返；共用测试组双跑 | 几十，秒 |
| API（httptest 加真库） | 契约、认证中介层、错误映射、公司隔离 | 每端点一两条 |
| 跨端 E2E | 接力流程与设备特有风险 | 个位数，分钟 |

不一层层叠同样的案例：规则错了第一层看得到就只放第一层。前端薄、没有业务规则时，传统前端单元测试没东西可测；只做复杂表单的组件测试，其余靠严格类型加契约生成类型、E2E 打真 API。

## 六、前端薄化的实际约束

- 前端只渲染后端回的 `allowedActions`、投影与必拍键集合；发现"需要自己算才能画"就是后端投影缺栏位，回头补投影。
- lint 挡两类泄漏：按角色或阶段字符串决定可否操作的比较；照片槽位之类的键名字面值（唯一来源在后端，前端只留显示标签对照表）。
- 认证走 HttpOnly Cookie，CSRF 用自定义标头加 Origin 允许清单；移动端与桌面端工作阶段长度不同，但到期与延长规则只在聚合一份，中介层只问它；认证中介层用只读查询取单笔工作阶段，需要延长才载入整个聚合。

## 七、本地测试入口

- 单一 Caddy 入口承载两端静态资源、`/api`、以及对象存储的 bucket 路径；TLS 由外层终止。对象存储签名 URL 的 Host 必须与浏览器看到的入口一致，反向代理转发附件路径时保留含端口的 Host，否则 SigV4 校验失败。
- 种子按 API 的允许来源设置 bucket CORS，所以种子与 API 必须用同一组来源与端点配置启动。
- 服务端自己也经公网入口访问对象存储时，主机要能解析该入口名称。
- 中间件启动后要等健康检查再跑迁移；可重建环境停止时数据库与对象存储数据卷一起丢，否则下次种子的 `If-None-Match` 上传会 412。
- 登录限速按账号计数会在多个审查线程共用环境时互相干扰：给每个线程分配不同账号，各登录一次后复用 Cookie。

## 九、视觉比对门禁

- 两层比对分开：结构比对以每轮本地建置的原型 DOM 骨架为基准（landmark、标题、区块、页签、主按钮、阶段标签的 computed 色，按 DOM 顺序），像素比对以入库的正式版截图为基准。原型截图不入库，数据值不进骨架。
- 首次上门禁必然全红。用棘轮：已知差异入库成清单，每笔带状态、精确差异行与理由，门禁只对清单外的行变红；清单只能删行或等长替换，不能加行。"更新清单反映现状"是子线程的默认诱惑，要在任务里明说不接受。
- 清单里的"必要差异"要写具体理由（真实登录 vs 示范入口、种子筆數、隐私页签不投影、授权投影），不留"待修"字样；每笔是日后审查的依据。
- 像素基准必须在固定渲染环境产生：本地与 CI 都用同一 Playwright 官方容器跑浏览器，宿主保留服务与 runner；否则字体与抗锯齿让全部状态失败。不要用 CI 产物覆盖本地基准，也不要放宽阈值。
- 门禁测试自己会撞登录限速：各角色登录一次把 storageState 存磁盘重用，worker 重启不再登录。
- 前端派发任务要求"先读"附页面×角色×阶段对照表、"交付"附受影响状态的并排截图，缺一退回；门禁上线后殘差修补的派发按清单逐笔做，完成判据是清单行数。

## 八、踩过的坑

- 把客户对"大约几张"的容量估计写成硬上限，与客户自己画的必拍清单冲突；估计只能当容量假设，规则来自作业描述。
- 文档内部不一致（导言写简化版、表格写精确版）会被实现照导言做；表是规则，导言要改。
- 全局 CSS 覆盖第三方动画在"减少动态效果"系统设置下让弹层定位失效；用主题 token 关动画，lint 禁通配选择器覆盖。
- 代理产物目录（`.amp/`、`.worktrees/`、本地测试目录）没进 prettier 与 git 忽略，会卡住所有提交。
- 子线程 provider 中断（额度、满载、串流断线）是常态：每次失败先把 worktree 改动提交成 WIP，再带着"从该 commit 接续、不要重做"的任务改派下一家；收尾阶段降为 simple 难度派便宜模型。
- 子线程连续小 push 会不断取消前一轮 CI；任务里写"本地全绿后一次 push，之后的修正先列出等裁决"。
