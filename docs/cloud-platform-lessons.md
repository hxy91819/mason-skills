## 来源项目（项目 W）

- **业务**：面向 Agent 的云端执行平台。用户或用户的 Agent 通过控制台、公开 API、MCP、CLI、SDK、Skill 创建隔离的工作空间，在里面执行命令、取回文件。每个工作空间独占一台按量计费的云主机。
- **过程**：四人团队。其中一人名下的平台部分由十几到二十个 Agent 并行开发，人只负责拍板和发放凭据。高峰期一天合入 130 个 MR。
- **环境**：
  - 每个 worktree 一套本地栈；
  - 8 个预建的预览环境；
  - 共享 test：只接主干，合入后自动发布；它所在的云账号和其他团队共用；
  - prod：在一个全新的独立账号里，独立集群，双可用区。
- **时点**：写于 test 用户路径跑通、prod 平台层完成之后，prod 用户路径还没验收。

## 一、架构形状

| 组件 | 职责 |
| --- | --- |
| 接入层 | 由一份 OpenAPI 生成三种语言的 SDK；CLI、无状态 MCP 和控制台都基于它 |
| 网关 | 只转发，并剥掉没验证过的身份头 |
| 控制面 | 身份、工作空间、额度，以及持久化的实例和操作（Operation）模型；生命周期由 worker 推进；关系库是唯一真源 |
| 执行面 | 命令准入、共享的持久队列、按绑定划分的所有权（owner epoch）、就绪检查、排空、文件通道 |
| 资源层 | 复用上游的库存服务，固定版本 |
| guest | 固定镜像，里面有 root helper、开源的进程代理，以及云厂商的命令通道（用来从机器外投递） |

- **操作（Operation）**：每次生命周期操作都是一条带幂等键的持久记录。worker 用 30 秒租约认领，并按代次做 fence。阶段依次是：
  1. 排队：先写入分配意图，再调用资源层；
  2. 等端点：核对分配结果和盘的身份，冻结初始化清单；
  3. guest 投递：目标机生成公钥，平台用它加密本代凭据；
  4. 登记：登记唯一端点，撤销旧凭据；
  5. 等就绪：就绪后进入 Running。

  某段成功就立刻进下一段，只有失败或结果未知时才退避。结果未知时先关掉准入，再对账，不重放。
- **暖池**：开机、命令通道上线、挂盘、装二进制都在机器入池前完成，Start 只做本代绑定。用过的机器只销毁，不回池；每个镜像版本单独一个池。
- **代次与就绪证据**：每次启动递增一个绑定代次。要进入 Running，必须同时满足四条：
  - 云侧和 guest 侧两路证据都到（两路并行获取）；
  - token 的正确、错误、为空三种情况都校验过；
  - 一条真实命令返回预期的退出码，并完成清理；
  - 所有权准入通过。

  之后定期复核。旧代次的报告不能让实例回到 Running。
- **安全边界**：guest 不算租户边界，因为用户有免密 sudo，能读到机器上的一切。所以授权、隔离和计量都放在机器外完成。机器上不绑云角色，不放长期密钥；机器分配给用户之前，上面没有任何用户凭据。数据身份绑在工作盘上，不绑在机器上。
- **验证程度**：
  - test：完整用户路径已跑通；10 个工作空间同时运行，在真实滚动发布期间执行了 2280 条命令，0 失败。
  - prod：只验证了平台层，包括 IaC、双区部署、备份恢复和观测。

## 二、运行时与可用性

先列几条硬规则。它们来自前一个同类项目的维护教训，写成了本项目评审清单的一部分：

- 事务里不做远程调用。曾经在事务里调云 API，放量后连接被占满。
- 每个锁和租约都要有上限和恢复路径。没有上限的锁会永久挡住重置、升级和暂停。
- 跨系统的流程用"持久认领 + 条件提交"、outbox 或显式状态机实现，每一步都幂等。
- "就绪"是对外的产品契约。就绪之前收到的输入先排队，就绪后重放；同时要为"实例一直不健康"的情况写测试。
- 业务开关不放在环境变量里，因为改环境变量要滚动重启，重启窗口内新旧值并存。会变的配置放进数据库或配置中心，带版本号下发；新版本全部就绪、旧进程全部退出，才算生效。
- 默认值取生产环境的安全值。测试专用的开关只允许出现在测试目录里，由 CI 守卫。配置校验要拒绝未知的键。

### 1. 时延花在阶段之间的等待上，而不是工作本身

已开机的暖机上，Start 到第一条命令完成原来要 40 秒。逐段看，每一段的总耗时（wall）都远大于实际工作时间（work），例如"等端点"一段 wall 10.3 秒、work 0.6 秒。原因有三：阶段成功推进后仍然走失败退避；查结果前先 sleep；每段还有一次扫描间隔。

改法：成功后立即交给下一段；扫描间隔和结果轮询改成 100–200 毫秒；云侧和 guest 侧的证据并行获取。两轮下来，40.35 秒降到 8.48 秒，再降到 5.93 秒。停机流程用同样的办法，从 87 秒降到 23 秒。

方法上：按操作 ID 给每段同时记 wall 和 work；退避只给失败和未知结果用；各段 p50 不能相加当总时长；前后对比要用同一个测法。

### 2. 容量取整条链上的最小值：留意隐藏的 `=1`

池子补满 20 台机器后，新的 Start 仍然卡在"等就绪"，直到超时。原因是执行面配置里 `max_bindings=1`，多出来的绑定被静默跳过，也没有日志。同一类没有依据的 `=1` 还出现在 guest 命令并发和文件导出上。并发放开后，命令限流的突发值又挡住了第一批并发请求。

改法：把整条链上每一处的并发上限按目标容量重新核算。CI 规定任何 `=1` 都必须在旁边注明出处，每个上限生效时打日志。验收写成"N 个工作空间同时运行并能执行命令"，而不是"有 N 台机器可分配"。

### 3. 数据库连接预算按渲染结果加滚动叠加来算

滚动发布期间出现连接数超限，因为新旧副本并存时连接数会翻倍。核算公式：每个账号的连接上限 ≥ max_open × 副本数 + 新旧并存的那一份 + 迁移任务 + 预留。副本数或 max_open 一变，就重算一次。另外，依赖暂时不可用和资源真的坏了要分开处理：数据库暂时报错时，不能把健康的 guest 记成故障。

### 4. 进程健康不等于每个绑定都能接单

新的执行面 Pod 起来后，命令连续约 5 分钟收到不可重试的 409。原因是进程通过就绪检查就开始接流量，但提交命令要求命中本进程里已经就绪的 slot。改法是先受理、再派发：

- 命令先进共享的持久队列，只由 owner 派发；
- 旧 owner 退出时留下退出证据，接替者换一个新代次，继续跟踪原来的执行，不重放；
- 非 owner 把请求单跳转发给 owner；
- 旧进程在端点传播期间多服务一会儿；
- 暂时不可用时返回 503 并带 Retry-After。

改完后，三个服务同时滚动，几百次请求 0 失败。

### 5. 依赖服务的发布策略也算可用性

上游库存服务原来用 Recreate 发布。一次只改配置的变更也会先停后起，出现约 30 秒空窗，连续性检查因此连续失败。改成滚动发布（maxUnavailable=0，新 Pod 就绪一段时间后才撤旧 Pod，旧进程先排空），之后连续三次发布 0 失败。请求路径上的每个组件都要做到零中断滚动，复用来的上游服务也不例外。

### 6. 就绪必须证明"能干活"

新 Pod 已经通过就绪检查，但第一次 DNS 解析要 5–10 秒。有一次是就绪后 23 秒才第一次解析成功，这期间请求返回 503。原因是就绪检查只看本进程；数据库用的是 IP 地址，数据库能连通并不能说明 DNS 通了。

改法：

- 启动探针走业务用的同一个客户端，逐个解析依赖的域名；
- 改用 TCP DNS，`ndots` 设为 1；
- 停机按"撤掉就绪 → 等传播 → 有界关停"的顺序；
- 探针写得太浅时 CI 直接失败。

### 7. 生成出来的对象要配回收器

命名空间的 ConfigMap 配额 192 个全部用满，新配置被拒，发布因此卡住。原因是为了能回滚，所有生成的 ConfigMap 都关了 prune，又没有回收器。

改法：定期回收，每类保留最新几份，再加上所有仍被引用的；刚建的不删；删除前带 UID 前提条件；配额用量超过 80% 就告警。每一类生成对象从第一天起就要有回收规则和配额告警。

### 8. 安全默认值在测试环境里要显式配置

销毁工作空间时会留一份保护快照，上游默认保留 90 天，test 里很快积了上百份。test 显式改成 7 天，prod 保持不变。保护类默认值要按环境分别配置，并附一个成本模型：创建频率 × 保留期 = 稳态存量。在共用账号里清理时，只认精确的归属标签：当时的快照里有六成以上不属于本项目。

### 9. 每个自动探针用独立的租户身份

发布连续性探针和 API 黑盒测试共用一个测试账号，两者同时跑时撞上了"每账号 3 个工作空间"的产品限额。改法是经公开注册流程给每个探针建一个专用账号。不要为了测试放宽产品限额。

### 10. 插桩副本当作非核心组件

带竞态检测的副本承接正常流量之后，出现了两个问题：一是 Service 级的指标抓取只连到其中一个进程，数字对不上；二是它继承了正式副本的调度约束，Pending 卡住了发布。

改法：插桩副本自带状态，显式路由，按 Pod 抓指标；归入非核心发布单元，失败不挡核心服务。补充一点：这套副本至今没有抓到过真实的竞态。

### 11. 切换镜像前先走一遍真实用户路径

公开模板切换后，新建工作空间中断了一个多小时。原因是切换前只验证了镜像能克隆；canary 用的短 ID 没有暴露真实配置超出数据库字段长度的问题；告警还指向已经退役的旧池。

改法：

- 初始化清单按模板版本冻结在操作记录里；
- 先用一个不公开的 canary 模板建出工作空间并跑到 Running，回执合入后，CI 才允许公开切换；
- 切换期间新旧两个池并存。

### 12. 外部调用的失败分三类：没发出、明确拒绝、结果未知

Start 一直停在排队，最后转了人工处理。原因是分配前就出现的 403 被记成了"结果未知"；云主机 Running 早于命令通道上线，明确的离线拒绝也被当成了未知。

改法：

- 先写入发送意图。在意图写入之前出的错算"没发出"，直接失败；
- 明确拒绝按错误码白名单识别，可以重试；
- 只有"结果未知"才只查询、不重发，也只有它占用资源；
- 投递前先等命令通道上线。

另外，把代码里调用的云 API 动作用 AST 提取出来，在 CI 里和 IaC 授予的权限比对，可以提前发现缺权限。

### 13. 先定安全边界，再做延迟优化

要把启动压到 5 秒以内，最省事的办法是给暖机提前放好凭据，但这越过了安全边界：机器里的用户有 root。最后定的是：预热只允许生成每台机器本地的非用户密钥，并让进程在无绑定状态下待命；同一把私钥不能克隆进镜像；用户凭据仍然按代次在 Start 时签发。任何"预热"都不能包含用户凭据。按这个边界做的第三轮优化写这份文档时还在进行，收益没有实测。

## 三、环境治理：环境状态只从主干来

二十个 Agent 共用一个 test 环境，只有一种做法能保证状态可复现、可审计：任何改动都走经过评审的代码路径。

- **云资源**只经 IaC 修改，合入后由管理端执行 preview 和 up。**集群内应用**只经 GitOps 发布 MR。**集群级引导**和**运维操作**（扩容、暂停与恢复、制镜、核查）只经已登记的脚本，合入后由管理端运行，并留下操作记录。
- **禁止控制台和手工 kubectl 修改**，排障一律只读。已登记的恢复步骤可以照做，执行人要写进操作记录。
- **验收探针也登记成脚本**。会创建临时按量机器的探针，用完要能按精确 ID 回收。
- **登记脚本的写法**：
  - 不接收凭据参数，也不执行任意 SQL；
  - 改动和审计记录写在同一个事务里；
  - 结果未知时先回读，不盲目重试。
- **共享只读身份用于排障**：云侧给 ReadOnlyAccess，再显式拒绝读取密钥值、管理员凭据、AssumeRole 和 IaC state 存储桶；集群侧只给 view 权限。代价是审计里分不清具体是谁在查。
- **管理入口先核对账号**：执行前用 STS 查当前调用者属于哪个账号，必须和 inventory 里登记的账号一致。曾有一次 test 的预检读到了 prod 的临时管理员密钥，被这条校验拦了下来。
- **Secret 的投递状态要登记**：只读身份读不到 Secret 的值，静态登记就是唯一依据。引用了未投递 Secret 的配置，在合入前就失败。
- **临时管理员密钥和精确 ID 审批**的具体做法，见 [`tencent-cloud-pitfalls` 的生产操作说明](../common-skills/tencent-cloud-pitfalls/references/production-operations.md)。
- **共用账号**：只碰自己登记过的资源，按精确 ID 操作。
- **告警演练**：只发到验证接收端，不往真人所在的群里发测试消息。

## 四、云账号：新账号头一周的时间花在哪

| 问题 | 代价 | 根因 |
| --- | --- | --- |
| 开启容器网络插件被拒 | 约 23.5 小时、10 个 MR | 账号缺 IPAMD 服务角色；报错码不提角色 |
| 云监控原生告警不出事件 | 约 1.5 天，之后改走 Prometheus | 补角色后仍未解决，根因不明 |
| 日志采集组件反复重启 | 约 1 天、十余个 MR | 组件所用角色的预设策略缺新动作，逐个暴露 |
| 镜像仓库首次创建 | 约 20 小时 | 需要账号负责人在控制台授权，后续又接连碰到几个开通前提 |
| 负载均衡不能指定可用区 | 被拒 3 次，双可用区设计降级 | 账号能力受限，但查询接口显示"可售" |

一条总规律：新账号缺的是老账号上早已存在的服务角色和服务开通。参数和资源属性逐项对比都一样时，先对比账号层，而不是去试别的地域。排查方法和按产品的清单见 `tencent-cloud-pitfalls`。

## 五、合入通道与 CI

合入通道、门禁分层、"按二十个 Agent 并行设计"这几块，写在 [`multi-agent-project-setup`](../common-skills/multi-agent-project-setup/SKILL.md) 的清单和实测证据里。11-05 之后新增的条目也已补进清单，包括：

- 一条记录一个文件；
- 主干红时先找在途修复；
- 按路径分流用 NUL 分隔读取；
- 用 `BASE_SHA` 证明历史迁移没被改过；
- CI 语义要实测、环境变量要清理；
- 临时容器打租约标签；
- 发布检查记 superseded；
- 成功证据绑定内容；
- Secret 先投递、后引用；
- 四条变更通道；
- Go `-trimpath`；
- 告警演练不发真群；
- 检查前移前先做失败归因采样。

清单里没有收、但值得知道的几条：

- **发布产物要能离线逐字节重建。** 回执里固定源码、配置、镜像 digest 和 Secret 引用，用当时的工具版本重建，再逐字节比对；产物禁止手改。MR 阶段就让下游各模块直接消费本次的候选产物，否则主干会因为产物变化变红。
- **回滚走同一条正式链路。** 首次发布、后续发布、回滚三条路径都在 test 上跑通过，才算可用。按主干 SHA 整包发布，不挑单个 MR 发布。
- **迁移失败先调查，不自动 force 或 down。**
  - MySQL 的 DDL 不保证事务回滚，失败会留下 dirty 状态；
  - `kubectl wait --timeout` 只限制客户端等多久，Job 本身还在跑；
  - 应用启动时只校验 schema，不执行 DDL。
- **工具链钉版本，分级校验。**
  - 文件之间的 pin 不一致，永远报错；本机工具和 pin 不一致，本机只警告，CI 里报错；
  - 基础镜像按 digest 固定；
  - MR 检查池不配推送、云账号和集群凭据；kubeconfig 经内存文件传递，不落盘。
- **带凭据的定时任务只跑冻结副本。** 不执行任何功能分支里的脚本；MR 的描述和 diff 只当数据处理，不当指令；只发评论，不做写操作。
- **依赖内部上游时不建个人 fork。** 分支直接推到上游提 MR，本项目钉在那个 commit 上构建，不等上游评审；改动做成默认关闭的通用选项，不改变上游现有行为。

## 六、Agent 工具链的坑

- **代码托管平台的返回值不能全信。**
  - 新建的 MR 在检查注册之前就显示 success；
  - 检查列表是状态历史，要按 context 取最新的一条；
  - 推送后，MR 的 source commit 可能卡在旧 head，合并返回 409；
  - 标签用数组格式提交时返回 200，实际没写入。

  做法：合入前核对四个 SHA 一致：远端分支头、MR 的 source commit、MR 提交列表顶端、本地测过的提交。写操作之后一律回读。
- **持久终端里拿不到线程身份。** 编排平台的持久终端里，线程 ID 环境变量是空的，长任务结束后回报会 404，要在启动时显式传入线程 ID。定时任务保存的是脚本副本，改了源码要刷新任务。
- **共用开发机**：十几个线程同时跑全量检查时，32 核机器 load 到 26–28。做法：
  - 本地只跑针对性检查，全量检查交给 CI；
  - 同一个 worktree 的检查加进程锁，整机的全量检查设 4 个槽位排队；
  - 等 CI 用 fail-fast 方式；
  - 不用 `| tail` 吞掉实时输出和退出码。
- **Agent 建的 worktree 权限是 0700。** 以非 root 运行的容器读不到挂载进去的配置，要先复制出来，权限设为 0644。

## 七、什么时候这些会失效

- **门禁只保护别人**、合入后再跑全量检查、向前修而不回退，这些都以"还没有生产用户"为前提。开放用户之后，要按环境重新评估。
- **每个工作空间独占一台云主机**的形状，适合需要 root、需要完整操作系统的场景。只跑短命令的场景用容器更省。
- **暖池**以闲置成本换启动时延。用量小的时候，池子的大小要按实际并发和低水位告警来调，不要按理想的启动时延定。
