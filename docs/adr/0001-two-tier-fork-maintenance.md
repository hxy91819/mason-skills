# Fork 维护：独立来源，按需领域聚合

2026-09-21 · 已采纳

这是一份供人查阅的决策记录，不属于 Agent 每次执行的必读材料。具体操作由技能负责，当前项目状态以项目登记表和发布记录为准。

我们维护多个长期 fork，既要跟上上游稳定版，又要保留逐项回馈上游的能力。每次升级都 rebase 所有功能分支，会反复处理共享接口的冲突；把功能直接合成大分支，又会让独立贡献难以提取。

我们选择：**feature/fix → 可选的领域层 → 冻结发布清单 → aggregate**。

| 部分 | 决策与理由 |
| --- | --- |
| 一级 feature/fix | 保存每项功能或修复的独立意图、补丁和测试，方便向上游贡献。休眠来源不随每次稳定版升级强制 rebase；继续开发时按需要适配。 |
| 二级领域 | 把反复共享兼容工作的一组补丁放在一起，集中适配上游版本。新增产品行为仍回一级；领域按实际耦合划分，不按目录机械拆分。 |
| aggregate | 是发布组合，不是新的产品开发层。默认基于上游稳定 tag，锁定补丁、依赖和来源映射；贡献时提取目标功能及必要依赖，不提交整个领域或 aggregate。 |

小 fork 可以一直直接集成一级补丁。领域层应当节省适配工作，不要求每个项目凑齐同样的领域。

**新项目**从稳定基线、独立来源和登记表起步，出现重复的共享适配工作再建领域。

**老项目**先保留当前可用版本和历史凭据，在原基线上盘点补丁归属，选一个合适领域试点，其余继续直接集成。完整重建应包含产品代码和维护文件；证明与预期快照一致后，再单独升级上游。没有合适领域时，只迁移登记和重建方式也可以。

可追溯依靠明确的补丁归属、冻结清单和能取回历史对象的引用。可打包依靠针对确切源码的真实构建证据；源码一致、构建成功、已发布和已部署分别记录。有数据库的项目还需验证真实旧 schema 与迁移记录，不能只测新建空库。

跨项目共享的是维护方式，各项目保留自己的构建、兼容性和部署流程。在 BB 中，`open-source-fork-maintenance` 管来源、聚合和发布；以本机 BB 服务为目标的打包及切换，再衔接 `local-aggregate-deploy`。

这个选择用少量登记和映射维护，换取更少的重复适配，同时保留独立贡献能力。它不会消除冲突，也不保证提取出的贡献无需再次调整。领域之间若长期互相牵制，应重新考虑边界。

后续若改变这些选择，另记新的决策并说明替代关系；日常 SHA、命令和打包结果留在执行记录里。
