# 领域设计不跑偏：规则归属与守护机制

一个由 Agent 承担大部分实现的业务系统，怎样在几十个 PR 之后仍然让"规则在哪里、改了什么"一眼可见。本文是通用做法，来源见下节，项目细节已去掉。

## 来源项目（项目 Y）

本文经验来自一个私密项目，这里只保留与做法有关的轮廓，称为项目 Y：

- **业务**：B2B 多方协作的工单系统。一张工单在多家公司、多种角色之间按固定阶段流转，每个阶段有回报表单、附件与按角色不同的可见范围；一个客户、一期范围、二期预留外部系统对接。
- **后端**：单体 Go 服务 + PostgreSQL + S3 兼容对象存储。聚合导向的领域模型，单一限界上下文：规则只住聚合、用例只编排、读写分路、聚合根带版本；OpenAPI 契约生成两端类型。
- **前端**：桌面运营端（React 18 + antd）与移动现场端（React 18 + antd-mobile）两个应用，共用呈现层包与 API 客户端包；同栈点击原型先经客户确认，之后作为规格而非代码。
- **过程**：Agent 承担大部分实现与审查，人只裁决规则与范围；需求链是客户原始材料 → 决策记录 → 领域文档 → 编号测试；所有检查从单一命令入口进 CI；本机测试环境经单一网关对外。
- **规模与时点**：一期约三十个功能项、七个聚合、二十余个 PR；文档写于一期功能完成、客户验收前。

## 一、问题

传统"一表一个 DAO、一个 Service"的写法，同一条规则（谁能看哪段、什么状态能做什么）散在多个 Service 与查询里。需求一变，要靠人读完调用链找出被打破的假设。Agent 实现时风险最高：它不读全系统，会在最近的地方再写一份规则，审查者看不出来。

目标不是完整 DDD，是三件事：规则只有一份归属；改动范围在 diff 里可见；Agent 不理解全系统也不会把规则写错地方。

## 二、规则住哪里

1. **规则只住在聚合。** 状态转换表、可见范围、派生规则、不变量，全部是聚合方法或领域函数，各只有一份。聚合是纯内存对象，不 import 仓储、HTTP 或其他模块；仓储整个加载、整个保存。
2. **聚合方法只有两类**：改自身状态的命令方法；把自己投影成某个帐号可见内容的 `ViewFor(actor)`，同时算出 `allowedActions`。聚合没有"编排"方法。
3. **用例只编排。** 命令用例：加载 → 调聚合方法 → 一笔事务内保存 → 回 `ViewFor`。查询用例：加载 → `ViewFor` → 按结果决定要不要向别的模块取读模型 → 组 DTO。用例可以按聚合回答的问题分支（`computer.NeedsLink()`），不得自己比较 `stage`、`role`、`ownerID` 这类字段。
4. **读写分路。** 读没有不变量要守；列表查询用领域定义的 `VisibleScope(actor)` 交给仓储翻成 SQL 或谓词，规则定义仍只有一份。跨模块拼装只在查询用例发生，聚合不查别的模块。
5. **认证在中间层，授权在聚合。** token 换帐号是平台事；这个人能对这张单做什么、看什么，依赖单据数据，所以在聚合。

## 三、规则还是呈现：一句判准

一条逻辑放聚合还是放查询，问：**两个页面各算一次、结果不同，算不算 bug？** 算，是规则，放聚合；不算（排序、分组、格式、只给一张报表用的统计），放查询。拿不准放聚合，代价只是多一个小函数。单一消费者的报表算法允许留在查询，PR 说明注明"只有 X 页用"；出现第二个消费者时搬进领域。

这句判准同时给审查用：审查者问同一句话，不需要理解全部业务。

## 四、事务与并发

- 一个用例一笔事务，可跨多个聚合。单体单库不采教科书"一事务一聚合＋领域事件最终一致"，事件只增加排错成本。
- 跨聚合唯一性（编号递增、某范围内编码唯一、一张卡同时最多一笔未释放分配）由仓储在事务内用计数表锁或唯一／部分索引保证；聚合只校验值的格式。
- 每个聚合根有 `version`，仓储的 `Save` 用 `UPDATE … WHERE version = $old`，影响行数为 0 即回滚并回 409。在仓储写一次，所有用例自动具备；同时挡并发事务与过期页面的提交。
- 多张表拼成的聚合，命令路径加载时另锁根行，否则两个 statement 之间被另一事务插入提交会间歇失败；查询路径不加锁。

## 五、七项守护，全部进 CI

任何一项列为"建议"而非 CI 必过，即视为未建立。

1. **不变量追溯**：领域文档里每条转换、可见范围、不变量有固定编号（冻结，不重排）；聚合测试用例名带编号；脚本检查"文档有编号、代码无测试"与反向。
2. **import 方向 lint**：领域包不得 import 仓储、HTTP、其他模块；用例不得 import 数据库驱动与 HTTP；handler 不得 import 领域常数。Go 用 depguard，前端用 dependency-cruiser。
3. **禁止位置 lint**：handler 与查询用例出现 `.Stage`／`.Role`／`.OwnerID` 的比较或 switch 即失败（Go 用 ruleguard 匹配 AST 模式，限定路径）。前端对应：禁止按角色或阶段字符串决定可否操作的比较；禁止后端拥有的键名字面值（照片槽位之类），前端只留显示标签对照表。
4. **双仓储同套测试**：用例测试同时跑内存版与数据库版，保证 `VisibleScope` 翻译一致、版本冲突真的回 409。内存版先行，不变量测试不碰数据库就跑完；表结构等聚合稳定再定。
5. **需求变更固定路径**：来源回复 → 决策记录 → 领域文档改那一条 → 对应测试改红 → 聚合改绿 → 决定是否回补原型。派发说明注明"对应领域文档第几节第几条"。
6. **领域专项审查**：三问——这条逻辑两处算得不同算 bug 吗；这个用例加载了几个聚合；有没有用例自己比了字段。审查者可以是 Agent，做成 skill 在每个后端 PR 后派发。
7. **全部必过。**

## 六、让 Agent 自己意识到"这会动领域"

守护只能事后抓。更前面一步是收到任何来源的需求（用户、客户回复、另一个线程、bug 描述）时，开工前先做领域影响评估，写进 Agent 入口文档：

1. 抽出需求里的名词与动词，对照术语表、转换表、不变量清单。
2. 定级：名词动词都在、只是规则内容变＝小改；名词在而动词不在、或聚合边界要动＝中改；名词都不在＝大改。拿不准按中改。
3. 回给提出者固定格式的评估（级别、新名词、新动词、触及聚合、触及不变量编号、下一步），再动手。
4. 小改直接走"文档改那一条→测试红→聚合绿"；中改以上停在评估不写代码，开 issue 贴 `needs-domain-review`，提醒人在团队内发起评审，结论落成 ADR 与领域文档后才动程序。

效果：人只在"规则本身要变"时被打扰；其余由 Agent 按文档裁决、事后报告。

## 七、什么时候该推翻

- 一个用例要加载超过三四个聚合，或版本冲突频繁：聚合边界画错，依领域文档重画，不是放弃模型。
- 出现第二个限界上下文（接财务、ERP）：再评估模块间用事件而非同事务。
- 需求歧义一律走决策记录，不由架构文档处理。

## 八、不适合的场景

规则少、读多写少的展示类系统；一次性工具；团队没有人能对"规则住哪里"做最终裁决。这套做法的成本是前期建模与七项守护，收益在第十个 PR 之后才显现。

## 九、实际经验

- 第一次领域专项审查就抓到三类错位：用例自己比字段、规则在两处各算一份、文档编号与测试对不上。lint 上线前靠审查，lint 上线后审查只剩"判准"这一问。
- 子线程最常见的越界是"为了过测试在查询里补一条规则"；禁止位置 lint 让它在本地就红。
- 文档内部不一致（导言写简化版、表格写精确版）会被实现照导言做；表是规则，导言要改。编号冻结后，改文档必须改到对应测试，这是追溯脚本在守。
- 聚合里的常量（默认数量、上限、槽位键）是前端最想复制的东西；全部走投影 API 回传，前端 lint 禁字面值，分叉就不会发生。
