# 客户确认原型复盘：用点击原型让客户把规则改定

这份文档记录项目 Y 从第一版点击原型到客户确认、原型冻结的过程经验，供下一个同类项目参考。它是复盘，不是技能；只保留可迁移的做法，客户材料、业务规则、真实名称与网址留在项目仓库。原型之后怎么进入正式开发，见 [原型到正式实现复盘](prototype-to-production-lessons.md)。

## 来源项目（项目 Y）

- **业务**：B2B 多方协作的工单系统。一张工单在多家公司、多种角色之间按固定阶段流转，每个阶段有回报表单、附件与按角色不同的可见范围。
- **原型**：同栈点击原型（React + 桌面组件库 + 移动组件库），全部数据在浏览器内存，发布到静态托管的公开网址；客户在即时通讯群里零散回馈。两周内发了四十多个小版本，客户多轮回馈改到实体与状态机，原型只有一处要改。
- **过程**：一个编排者会话负责分析与沟通，实现、审查与视觉优化全部派发子会话；人只裁决规则与范围。
- **结果**：客户确认后原型冻结当规格，正式开发对文档链不对原型。

## 一、原型回答什么问题

原型只做一件事：**让不懂技术的客户用点击确认规则**。角色、实体、状态机还会变时，这是最便宜的确认手段；文件客户不看，问卷回复率低，原型他们会一条条点。

由此推出三条边界：

- **一次性代码**。不写测试、不做错误处理、不接后端、不做持久化（localStorage 只为客户刷新页面不丢状态）。主仓库的 lint 与 CI 不扫它，它只有自己的建置、脱敏、CSS 与场景检查。
- **不做假后端**。曾讨论"前端正常做 + 假后端"，否决：客户每轮回馈都改模型层，假后端会让每次改动同步契约、后端、前端三处，返工的是一致性。真正的风险是正式开发时照抄原型前端的业务逻辑，这要用工具挡（禁止 import 原型目录、业务规则只在后端），不是靠换架构。
- **范围只来自原始材料**。分析层或 Agent 自己想到的功能（接单确认、改派、退回返工、通知、报表）一律二期，页面上不出现，只在数据结构预留。客户看到页面上有的东西就当成承诺；一次性需求单先做客户没提的功能，就是扩大范围。期别唯一来源是功能清单的一栏，其他文件只引用。

## 二、让客户看懂：示范层与产品层分开

客户要在没人陪的情况下自己点通一条流程。为此加的东西统称**示范层**，要在视觉上明显不是产品的一部分，并且能整体拿掉。

- **预览控制台**：悬浮、可折叠、可拖动的面板，集中"当前系统与人员、切换系统／人员、待确认清单、这张工单下一步该谁做、重设数据、清空数据从零开始"。曾放在页面顶栏与右侧固定栏，都被客户当成产品功能；固定右栏还在笔记本宽度盖住表单下拉。改成不占版面的悬浮面板，展开时有整页背板，点背板或任何导航动作自动收合。
- **下一步导引**：工单详情显示"你现在要做 X／等待某角色做 Y"并附一键切换到该人员，让客户不用记流程也能走完。导引文案出现在产品区域会被误解为产品逻辑，所以只住在控制台。
- **待确认标记**：页面上只标客户必须回答的题（黄色虚线"待确认 Qxx"），文字直接写出问题与我们目前做成的样子。客户没答、我们按默认定案的题，用控制台一个开关才显示（灰色"预设 Qxx"），默认关闭，客户看不到，内部检视影响位置用。题号与确认清单、决策记录一一对应。
- **确认清单页**：独立入口不进工作台。分三段：已照回复改好（免回复）、请回答（三四题是／否）、其余依默认（免回复、有误再说）。可勾选并生成回复文字一键复制或经即时通讯送出；静态站不收表单，客户贴回群里再归档。
- **版本与产品纪要**：入口页显示版本号与历次"产品功能变化"的纪要，用客户看得懂的话写，技术与部署细节不写。

## 三、没答的题按默认做进去，不要没完没了

客户的回复零散、只答一部分。等答案会把节奏拖死，所以：

- 没答的题由我们按"不加页面、不加角色、不加流程段"的那个选项先定，做进原型并标"暂定"，再出一版确认清单请客户确认一次。
- 客户答过一轮后，剩下的题从他的原话与既有工具**推定**答案并定案，在决策记录写明推定依据，不再开新一轮询问；只有推定会产生两种差很多的做法时才问。
- 真正要问的只留答案会大幅改结构的题，一轮不超过三四题；客户上一轮跳过没答的题（多半听起来像系统细节）不再重问，改成陈述句放"免回复、有误请注明"段。
- 确认清单附截止日与"未回复视为同意暂定"。范围题（数据迁移、通知、报表、台账）要在报价前问完。
- 明显的矛盾直接在原型里处理成一种做法，在待确认清单说明；客户觉得不对再改。

## 四、视觉优化的魔法提示词

视觉质量不靠描述"要好看"，靠给一个外部标准加自审循环。原话：

> 把現有前端設計品質標準以 awwwards、webby awards、FWA 獲得獎項的程度為目標，透過自我檢查，反覆自行提升品質，直到達到該品質標準為止。

它有效的原因是三件事同时存在：一个模型知道的外部标准（获奖作品的完成度）、一个明确的循环（渲染→自查→改进）、一个由模型自己判断的终止条件。派发时还要加一句验收标准：仍以这个业务系统的信息清晰度、操作效率、桌面与手机体验为准，不以动画或装饰数量代替质量，否则会得到一堆特效。

配套做法：

- **独立分支、独立预览网址**。大改视觉前先提交一个"优化前基准"，让子会话在独立 worktree 做，发布到单独的预览网址，人把新旧并排比较后再决定转正。转正后把临时分支废弃，只保持一条主干维护原型。
- **转正后再做一轮减法**。获奖标准会带进"AI 套版痕迹"：左侧色条、背景光晕、渐层头像、浮起动画、标题小标、一排重复的指标盒子、卡片套卡片。转正后专门派一轮按反模式清单删掉它们。我们把这份清单与"以读者任务为起点"的方法整理成项目 skill（来源是一份公开的设计方法文档，去掉品牌专属内容），之后每轮视觉修正都按它自检。
- **页面上的否定句不合适**。"不做 X""不支持 Y"放文档可以，放页面上客户会不安；页面只写做成什么样。
- **版面原则比配色重要**。真正解决客户看不懂的改动是结构性的：一页只有一个"现在要做的事"（一颗主按钮）；可点的东西长得像按钮或链接，指派改文字链接点了才出下拉；只读面与编辑面不混（白底编辑面、灰底只读面）；进度条纯信息不可点，页签是唯一切换入口；表单只给当事人，其他人看同一区块的只读版，未到的阶段写"尚未开始"。

## 五、种子数据之外必须做空数据路径

原型有现成种子，客户一打开就有工单可点，这掩盖了一个问题：**产品第一天没有任何数据**。客户问"案场在哪里建"时才发现，页面之间有依赖顺序（公司→人员→项目→案场→库存→工单），而原型从没从零走过。

补的做法：

- 控制台加"清空数据（从零开始）"，与"重设数据"（回到种子）分开。
- 看板最上方一张"开始使用前"卡片，列出必须先建的几项，缺哪项就直接连到那一页；五项都有了卡片消失。
- 每个页面在前置数据缺少时写明先到哪里建（建单缺案场、备料缺库存、指派缺承包公司），不是空下拉。
- 写成一条场景（清空→一路建到第一张工单的某个阶段）固定跑，之后转成正式系统的跨端 E2E。

教训：原型默认展示"稳态"，但客户会问"第一次怎么用"，而依赖顺序正是领域模型的一部分（谁依赖谁）。

## 六、走查与截图要固定成工具

十个子会话 distill 的共同缺陷之一：每个子会话各自写临时 Playwright 脚本截图，截的视口、登录路径、滚动容器都不同，看到的问题互相对不上。固定成两个入口后才稳定：

- **场景脚本**：十来个从种子重新开始、可独立执行的场景（主流程、维修沿用、另一位 PM 的遮罩、收料差异、承包公司手机备料、照片查询、库存释放、从零开始……），断言失败非零退出并留图；每个场景对应一条客户确认过的规则。
- **截图脚本**：固定参数（账号、单号、页签、手机端、路由），自动建置或连既有预览、清 localStorage、从入口选系统与人员。手机端画面用桌面视口截（窄于某宽度会变全屏），长表单先滚内部容器再截；临时脚本放原型自己的 scripts 目录（ESM 依脚本路径解析依赖，放 `/tmp` 找不到包），用下划线前缀，跑完删除。
- **编排者的 review 循环**：子会话交付后，编排者用同一套工具到正式网址以不同身份截桌面与手机，逐条核对版面原则与反模式清单；有问题直接再派一轮，任务里写具体到组件的修法；每轮只在对话留一句进度，全部满意再给人一份带截图的总结。人授权这个循环"改到你满意为止"，但也明确"不能没完没了"：一轮再审后就发布。

## 七、发布脚本把人的检查变成门禁

原型是公开页面，发布错一次就是客户看到。发布脚本一条命令做完，并挡住过去犯过的错：

- **纪要必填**：没有 `--note` 不能发布；纪要里有禁用名称或简体字直接拒绝。
- **脱敏检查**：原始材料里有客户真实名称，很容易被带上页面。脚本扫可见源码与建置产物，命中禁用名单即中止；旧版浏览器里残留的 localStorage 数据由 store 载入时按稳定 id 覆写显示名，不靠客户手动重设。
- **CSS 检查**：禁通配选择器覆盖第三方组件动画（见第八节）。
- **版本写入顺序**：版本号与纪要由脚本写入，不手改；先写版本再建置再上传，失败用 `--retry` 沿用同一版，避免版本号与线上内容对不上。验版看线上 bundle 里的版本字符串，不看发布记录。
- **发布分支参数放 `.env`**：托管平台的"生产分支"参数一次漏设，发布只到了预览别名，正式网址没更新，客户看的还是旧版。写进 `.env.example` 与 README。
- **一改就发**：原型任何画面或行为修改，验证后立即发布，不再问授权；纯文档改动不触发。改了存储结构（存储键升版）要在纪要写"请刷新，旧的示范数据会重置"。

## 八、踩过的坑

- **全局 CSS 覆盖第三方动画**。视觉优化时加了一条 `@media (prefers-reduced-motion) { *, *::before, *::after { transition: none; animation: none } }`，在开了系统"减少动态效果"的浏览器里，组件库弹层的定位依赖其动画流程，下拉停在屏幕外，客户"选不了"。Playwright 默认环境重现不出来，差异就在这个系统设置。修法是用主题 token 关动画，stylelint 禁通配选择器与覆盖动画 class，场景脚本固定在 `reducedMotion: 'reduce'` 下跑并断言弹层在视口内。用户报"选不了"而本地正常时，第一轮就查这个。
- **多个并行会话各改原型**。合并时漏掉另一个会话及其三个子会话的改动，客户看到功能倒退。之后原型只在主干维护，派发前先对齐远端，主工作区里不属于本次的未提交文件全程不碰。
- **组件库命令式 API 在新版 React 下静默失效**。移动组件库的 Toast／Dialog 在 React 19 下不出现，没有报错；锁 React 18 并写进 README。
- **名词定稿晚于实现**。阶段名改了三次，每次改页面、文档、确认清单三处。术语只在一个文件，页面文案引用它；改领域规则（可见范围、必填、沿用条件）时同一变更里更新术语文件，不能只改画面。
- **子会话自行引入的决定没有汇总**。派发任务模板强制"自行引入的决定"在回复里单列，编排者逐条接受或退回，回报时列成"已决定，不同意再改"，不混进待决清单。
- **客户的估计被写成硬规则**。"大约几张照片"被写成上限，与客户自己画的必拍清单冲突；估计只能当容量假设，规则来自作业描述。
- **文件和原型打架时谁对**。原始材料是证据，决策记录里的裁决才是规则；文档与原型都必须和裁决一致，没对上的一方是 bug；没有裁决的就是未决。客户前后两次说法不同时，以后一次为准并记录改口。

## 九、冻结与交接

客户不再改实体与状态机时，原型冻结：之后只修示范错误，新需求走决策记录与功能清单，再决定是否回补原型。交接前写一份"原型里什么是规格、什么是示范手段"的对照表：类型定义与 reducer 的 action 是规格（每个 action 一个用例），授权判断函数是规则（搬的是规则不是代码），种子是测试数据范本，走查场景是验收剧本，视觉 token 与页面骨架抽成共用包，预览控制台、待确认标记、确认清单页、单文件 HTML 备份是示范手段，不搬进产品。
