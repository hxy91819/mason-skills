# 行为基线（behavior-baseline）：先留下答案的依据

读取 [共享规则](workflow.md)、[证据规则](evidence.md) 和 [基线报告模板](../assets/baseline.md)。

## 输入与权限

输入：固定旧版、批准范围／契约、测试环境、收益标准。允许在授权的测试准备分支增加测试和夹具，不改旧生产语义，不覆盖用户未提交工作，不碰生产数据和凭据。

基线不要求第一次穷举整个系统；但所有本次必须保持的契约都要有证据计划，不能以 P2 之名默许丢失已承诺的行为。

## 1. 找可信 oracle

对每个契约分别记录：

- **contract**：产品规则、协议、标准或经业务负责人确认的预期。
- **characterization**：旧实现实际观察到的行为，仅作为兼容基线。
- 规范与旧行为冲突：写入已知缺陷，说明保持还是单独修复由谁决定；没有批准前不混入本次重构。

依据必须指向可读取材料或实际运行。不能从候选代码推断正确预期，不能用 AI 共识替代业务决定。

## 2. 用稳定行为入口建测试

测试至少覆盖本次变化相关的正常、边界、错误、权限、持久状态和事件；并发／生命周期变化必须加相应时序与故障测试。

优先测试稳定公开接口和组件公开契约。保留少量关键端到端链路；不要把全部保证堆到慢而脆的端到端测试，也不把组件 mock 的返回值当真实数据库／任务链路证明。

写清断言：内容、顺序、错误类型、没有发生的副作用、最终状态。不要只断言 HTTP 200、非空、函数被调用或日志有关键字。

性能约束可以验证查询预算、批次上限、资源增长；这不是强行锁定私有函数拆分。业务测试应在旧版通过，新增性能目标允许旧版不满足，但必须单独标为 benefit 证据。

## 3. 控制比较条件

固定或记录时间、随机种子、初始数据库、时区、依赖版本、配置、外部服务响应和负载。新旧各自使用相同初始状态，不共享被前一次执行污染的状态。

差异测试先做旧版对旧版的重复性控制；若本来不稳定，先解释噪声。对允许变化的字段使用明确批准的白名单，不能为抹平差异把权限、金额、顺序、错误等统统删除。

旧实现必须固定且独立；两个入口同时调用已修改的公共内核不算独立对照。跨语言可用同一黑盒样本驱动，但适配层不得偷偷修正结果。

有副作用的生产请求不能执行两遍。使用隔离快照、录制响应、模拟下游或单写者设计；没有安全方案则不跑影子写入。

## 4. 验证测试本身

先让旧版业务测试成功，再针对高风险契约做少量红控：

1. 在独立临时工作树，从固定基线建一个刻意错误的实现，例如移除租户过滤。
2. 保持断言、夹具及测试发现配置不变。
3. 运行对应测试，确认失败是目标行为断言，而非编译错误、依赖失败或环境超时。
4. 保留错误 diff、失败测试名、日志、对应的原始基线和 reviewer 确认。
5. 不合并错误实现；不要用 reset 清掉别人的工作。

红控未抓到错误，修测试后重新跑旧版并再次红控。低风险契约可说明不要求红控；不要把全仓变异测试作为每次重构的强制成本。

## 5. 基线版本与封存

测试准备完成后产生固定 `base_revision`；审查 `origin_revision → base_revision` 只包含已授权的基线准备变化。必须改生产可测试性时，返回规划拆出小步骤，不将它算作测试文件改动。

用 [工具说明](tooling.md) 中的 `seal` 保存选定断言／夹具的 Git 对象和内容摘要。记录工具、策略、封存摘要，交给可信审批位置保管。摘要本身不等于审批。

用 `run` 记录实际测试；机器最终检查可读取 JUnit XML。项目不输出 JUnit 时可以用现有日志先分析，但自动门禁不能把缺少结构化执行证据算作通过。Python unittest 可用本 Skill 的 `scripts/unittest_junit.py`。

## 6. 交付与失败分流

`baseline.md` 和证据目录包含：

```text
契约 ID → 来源 → 测试/断言 → 夹具 → 实际命令 → 版本 → 结果
关键红控：制造的错误 → 哪个断言失败 → 排除环境错误的证据
收益基线：测量方法、数据规模、并发、重复次数、资源/延迟代价
已知旧 bug、不可控依赖、未执行／不稳定测试、剩余风险
```

输出 `BASELINE_READY` 仅表示本次要求的基线就绪；未知关键行为、旧版无法构建、测试没有实际运行或没有可信 oracle 时输出 `INSUFFICIENT`，给最小补证或缩范围建议。
