# 重构审查与独立验收：验收证据，不验收自信

## 已完成重构的事后 review

用户只要求 review 时，先确定旧版与候选范围（固定提交或含未提交改动的工作区），检查实际 diff、受影响调用方和现有测试／运行证据；按风险运行必要且可执行的检查。按严重程度报告具体发现（文件位置、触发条件、行为影响、依据），再说明已验证范围和未能证明的行为。没有发现问题时可写“未发现阻断问题”，但不能把缺少的基线或未执行的测试说成已验证。

此模式不要求补建工作单、`policy.json`、`seal.json` 或事前基线；已有材料可直接使用。只有既有门禁材料完整且与固定版本对应时，`gate` 的机械结论才有意义；不能把事后审查写成正式门禁 PASS。用户要求继续修复或补齐证据时，再转到相应模式；review 本身到报告结论为止。

## 正式证据门禁验收

读取 [共享规则](workflow.md)、[证据规则](evidence.md)、[验收模板](../assets/verification.md) 和 [机器验收格式](../assets/verification.template.json)。以下步骤只用于正式验收。

## 角色与输入

默认独立会话；直接读取目标、可信策略摘要、固定旧版、最终候选版、实际 diff、影响报告、封存、运行日志和报告。编码总结只能作为导航，不能作为证据。

只写验收报告和本次验证输出；不得修改生产代码、批准策略、冻结断言或放宽测试标准。需要试验时在隔离环境进行；新增回归测试交回基线／编码步骤，测试后重新验收。

不能启动独立会话时明示限制；不得编造不同 reviewer ID。外部身份真实性由宿主核实，JSON 字段只是记录。

## 1. 检查对象和证据绑定

确认完整 SHA，不使用移动分支名代替旧版／候选版。确认实际测试的源码、依赖、配置、夹具与待验收版本一致。

检查工作区、暂存区、未跟踪文件、子模块和生成物；自动最终门禁要求干净且已固定的候选提交。不要自动 stash、reset 或提交用户工作来“弄干净”。

测试后修改代码、锁文件、编译配置、测试、夹具、公共依赖或合并基线，应重新执行受影响验证；自动门禁保守要求候选证据 SHA 完全匹配。缓存测试或仅树相同的例外不自行开放。

## 2. 从实际 diff 复核边界

逐项核对 actual 影响报告，不能只信其结论。关注删除和重命名的旧入口、公共默认值、共享缓存、数据消费者、异步／定时入口、迁移及配置。

批准路径内出现新的语义影响同样越界。必要消费者未知时不能按“未搜到”放行。范围扩大退回影响面决策，而不是在报告里轻描淡写成一个建议。

## 3. 检查每份证明是否真的成立

对每个契约回答：哪个测试、哪个断言、什么输入／状态、在何版本实际执行？正常、错误、权限、副作用及本次新增时序是否匹配风险？

特别识别：

- 测试绿但没有运行任何用例、全部跳过、只跑了子集或复用旧报告。
- 候选版只 mock 掉了真正改动的组件；测试没有经过新路径。
- 新旧实现偷偷使用同一被修改的内核。
- 删断言、扩大容差、更新快照、捕获并吞掉断言异常。
- 把红控编译失败／超时当测试有效，或用重试隐藏不稳定回归。
- 新实现符合旧 bug，却违背明确业务契约；需要独立决策，不强行二选一。

读原始日志，核对框架统计、失败和跳过。机器检查通过仅是结构和版本一致，不证明断言充分。

## 4. 收益和退化分开判断

验证原始收益标准，不接受“改成异步／加了批量／少了代码”替代测量。检查同一负载下的端到端延迟、吞吐、资源及其他业务退化。

性能数据不稳定时报告样本、环境和波动；没达到收益但行为通过，也不能宣称重构成功。结构收益可用可复现的架构检查证明。

必要时用 [领域清单](checklists.md) 查批量化、异步化、数据迁移和跨语言差异。

## 5. 给三态结论

- **PASS**：批准范围内的必要契约有当前有效证据；收益达标；无未处理阻塞；剩余风险明确。仅允许进入发布流程。
- **BLOCK**：发现违约、越界、受保护基线变化、目标明确未达或门禁被绕过。给具体修复／重新决策路径。
- **INSUFFICIENT**：oracle、消费者、环境、断言充分性、运行版本或必要执行证据不足。指出缺哪一块，不转成“应该没问题”。

多问题并存时，已证实违约优先 BLOCK；只缺证据则 INSUFFICIENT。低优先级残余风险可以被明确记录和接受，但不能伪装为已验证，也不能覆盖必要契约缺口。

输出 `verification.md` 便于人读；自动检查使用 `verification.json`。具体填写字段见模板和工具说明。运行 `gate` 后区分 `PASS_MECHANICAL` 与本阶段的语义结论。

## 6. 交接而不是擅自发布

确认是否提供数据兼容、灰度指标与停止条件、恢复路径。真实发布权限、审批、制品证明和恢复演练仍由既有平台验收。

发现恢复能力缺失时明确“代码验收／发布准备”分别处于什么状态，不凭一句“可回滚”声明可生产发布。不得未经授权触发双写、扣款、删库、更新线上配置或生产部署。

## 最终报告控制在一屏

```text
结论：PASS / BLOCK / INSUFFICIENT
版本：baseline → candidate
证据：关键契约、具体测试、实际收益
最重要缺口：链路 → 行为 → 缺的证据/发现的违约
建议：返回编码／返回基线／重新规划／进入发布门禁
剩余风险与发布限制：具体内容
```
