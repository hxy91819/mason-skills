# 证据规则

## 一条有效证据需要什么

行为契约 ID、断言来源、具体测试和断言、初始状态／样本、实际执行命令、固定源码版本、依赖与配置、运行环境、实际结果、完整日志及报告位置。不能只填一个“通过”。

本 Skill 的 runner 自动记录 Git commit/tree、命令 argv、时间、退出码、源码前后是否稳定、日志及 JUnit 摘要。环境描述由调用者提供，需要 reviewer 验证；它不是自动检测出的硬件隔离证明。

以下仍由 reviewer 负责：测试有没有断言正确内容，fixture 是否代表所需状态，命令是否真的运行目标实现，mock 是否遮挡缺陷，测量是否可比，外部服务是否受控。哈希和 XML 不能自动判断这些问题。

## 测试分层

- 行为入口：消费者实际看到的输入、响应、错误、授权、最终状态和必要事件。
- 组件契约：多调用方共同依赖的失败、排序、事务、取消、幂等和生命周期。
- 集成：验证本次改变的真实组成方式，不只 mock 组件。
- 非功能：查询量、批次、资源、延迟与架构约束，与业务一致性分开举证。

范围和测试深度按具体风险确定。路径／行／分支覆盖率只辅助发现遗漏；不把所有组合覆盖作为前提，也不把已知漏测称为验证完成。

## 红控

本 Skill 称 red control 为“在隔离旧版上故意引入一个应被捕获的错误”。必须满足：原版相关测试通过；错误版出现预期测试失败；错误不是环境、编译或测试发现失败；冻结断言没有变化。保留具体失败测试名和人工确认。

runner 对 `red-control` 接受非零退出码加 JUnit failure、零 error 作为机械条件；这不证明失败原因正确。reviewer 的 `red_control_confirmed` 不能仅因命令红灯就设 true。

## 旧版和新版差异

对照响应、错误、最终数据库、事件和关键顺序；控制输入、时钟、随机数、配置、依赖、初始状态。规范中本来无序的集合可按批准规则比较；不能为通过对照丢弃关键字段。记录允许差异清单及批准来源。

先做旧版对旧版控制。重复读可能产生不同世界状态；一月正常流量也不等于包含撤权、丢回包、取消、超时和罕见配置。

## 证据失效

自动 gate 对 candidate commit 不完全一致的候选证据一律拒绝。固定 baseline 的旧版证据仍可使用，但只有 policy 的基准和契约未变化、外部测量环境可比时才有意义。

基线预期／夹具／适配器修改后需重新跑旧版、重做相关红控、封存并批准新摘要。不能只重录快照。依赖、数据库种子、外部服务或性能硬件变了，即使 Git SHA 没变也可能失效；由 reviewer 显式检查。

测试写源文件或改变 HEAD 会被 runner 标记。测试产生 ignored 构建产物不一定改变 Git 状态，因此必须额外记录制品和环境；本 Skill 不是完整的可复现构建系统。

## 失败、跳过与重试

非零退出、测试失败和环境错误如实保留；重试追加新文件，不覆盖原记录。强制要求的测试全部跳过或一个未跑都不能放行。少量 skip 的理由由 reviewer 明确对应到非必要范围；不能通过去掉 test selection 隐藏失败。

自动报告要求实际 JUnit testcase 元素，并核对失败／错误／跳过；仅 `tests="100"` 没有 testcase 明细不会被认为有一百条真实测试。runner 不自动转换其他框架输出，请使用项目已有 JUnit exporter。

## 完成与发布

`PASS_MECHANICAL`：文件范围、固定基线、证据摘要和版本对应关系满足机械规则。
`PASS`：reviewer 判断必要语义／收益有充分证据。
`READY_FOR_RELEASE`：上述条件和交接材料齐全，可由既有平台决定放量。
都不等于生产环境已经验证，也不等于数学上的完全等价。
