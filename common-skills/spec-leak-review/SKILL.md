# Spec Leak Review

这是流程类 Skill，默认仅在用户显式调用 `$spec-leak-review` 时运行。

以产品经理视角审查一个界面：**页面上每一段文字、每一个展示元素，是否应该出现在目标受众眼前**。只读审查，不修改被审代码，产物是一份单文件 HTML 报告。

主审对象是 **spec leak**——写给实现者和评审者的需求文本（约束、边界、否定式免责、验收标准）被原样渲染成用户可见文案。模型生成界面时高频产生这类文字，因为它把需求文档当成了文案来源：需求里写"不修改配置"是给实现者的边界，渲染到页面上就变成了用户从未问过的问题的答案。审查范围不止文案措辞，也包括这个元素本身是否值得占用界面。

## 1. 确定受众与决策

先回答三件事并写进报告开头：谁会打开这个界面；带着什么疑问来；看完之后要做出什么决定或动作。

受众决定一切判定——同一句"清单摘要 975d85…"对终端用户是噪音，对值班运维是工作对象。无法从用户输入、截图上下文或代码判断受众时，先问用户，不要假设后展开审查。

完成标准：受众和"看完要做的决定"各能用一句话说清，且后续每条 finding 都能挂回其中一句。

## 2. 建立元素清单

双轨采集，两轨都有时交叉核对。

**截图轨**：界面能跑起来时，用 [`scripts/capture-surface.js`](scripts/capture-surface.js) 采集每个界面，得到全页截图和带文档坐标 bbox 的可见文本清单。它把 placeholder、`title`、`aria-label` 一并收进来，并标出元素是否藏在 `<details>` 里、字号多大——这些是第 4 步判定层级的依据。脚本落地在浏览器错误页时以非零码退出，此时截图不能当作被审界面的证据。

拿不到浏览器或界面跑不起来时，用用户提供的截图逐区域盘点：标题、副标题、卡片标题、说明文字、字段名、字段值、状态标签、按钮、空态占位、时间戳。看到的每一块可见文字都进清单，包括看起来无害的；坐标从图上量出来，后续标注同样可用。辨认不出的文字标注为不可辨认，不猜测内容。

**代码轨**：用截图里的文案原文在仓库检索定位组件与 i18n 条目，比按目录猜更可靠；每条给出 `file:line`。截图未出现的分支文案——错误态、空态、tooltip、loading——一并纳入清单。文案有配置或环境变量覆盖机制时，确认线上生效值，不要拿源码默认值当结论。

截图里有而代码里检索不到的，标注来源为运行时数据或后端返回。

界面有部分区域采集不到（需要鉴权、依赖外部网关、触发条件构造不出来）时，如实记录采集不到的范围和原因，写进报告的覆盖范围限制。不要用源码推断冒充真实渲染结果。

完成标准：清单条目数不少于截图中可见文字块数；每条要么有 `file:line`，要么标注为运行时数据或不可辨认；每条来自渲染面的条目都带 bbox。

## 3. 逐条判定

对清单每一条先归类，再给结论。七类 spec leak，按出现频率排列：

1. **否定式免责**——告诉用户"本页不做什么"。信号词：不会、不再、不读取、不显示、不同步、仅、只。用户不会主动担心一个页面不做的事，这类句子的真实读者是需求评审者。
2. **实现策略外泄**——把取数、路由、优先级规则当成用户说明。信号：按白名单、优先使用、只有…才、降级、回退、同步。
3. **验收标准当文案**——把"用于核对/用于确认 X 与 Y 是否一致"这类验收目的写成副标题。它描述的是测试要验证什么，不是用户能得到什么。
4. **元文案自述**——"这里展示…"、"本页用于…"。标题和内容本身已经表达了页面职责，再解释一遍是替产品经理讲解产品。
5. **内部代号与技术标识**——服务名、仓库名、组件名、hash、Release ID。受众不认识，或认识但无法据此采取任何动作。
6. **无动作信息**——只呈现状态不给下一步；异常时用户不知道能做什么；标识符不可复制。
7. **占位与调试残留**——`—`、`暂无`、示例值、TODO 文案随版本上线。

每条结论四选一：**保留 / 改写 / 降级 / 删除**。降级指移出主界面——收进 tooltip、帮助文档、日志，或仅内部和调试模式可见。

**防过度标记。** 以下情况判定为保留：

- 受众本身是运维或开发，技术标识就是他们的工作对象。
- 否定式陈述回答的是受众真实顾虑（隐私、计费、数据删除、权限申请），且此处是受众第一次可能产生该顾虑的位置。
- 标识符用于对外求助或提工单，且界面提供了复制入口。

判不准时按保留处理，列入报告的待确认清单，不为凑数量升级成问题。

**改写的硬要求**：每条"改写"必须写出可直接替换的完整目标文案，不写"建议优化措辞"。目标文案只描述受众关心的事实和可采取的动作，用陈述句表达该页面做什么，不用否定句表达它不做什么。

## 4. 视觉复核与定级

判定完先回到截图上，逐条把被判定的原文在真实界面里找到，用 [`scripts/annotate-shot.py`](scripts/annotate-shot.py) 圈出来。**在截图里找不到的条目，判定就站不住**：它要么在别的界面，要么根本不渲染给用户，退回第 3 步重新归类，不要带着"应该在那儿"的假设进报告。

排版会改变结论。locale 文件里相邻的两行，在页面上可能一行是占掉首屏的主副标题、另一行藏在折叠区里——源码看不出这个差别，截图能。定级以真实排版为准：

- 占据首屏主视觉、或字号层级高于它承载的信息量：升一级。
- 已经收在 `<details>`、tooltip 里，且入口标注了内部用途：降一级，或直接转为保留。
- 字号与层级和内容重要性不匹配，但文案本身没问题：单独记为层级问题，不要混进文案 finding。

三档定级：

- **阻断**：让受众误解产品能力或权限边界、暴露内部系统结构、占位残留随版本上线。
- **应改**：纯实现细节、元文案、无动作信息——占据主视觉但对受众无价值。
- **可选**：措辞与信息层级优化。

渲染面采集不到、或只出现在构造不出的分支里的条目，不做视觉复核，但必须在报告里逐条标明未截图及原因。

完成标准：每条来自渲染面的 finding 都有一张标注截图，且图中能看清被判定的原文；其余条目都写明了未截图的原因。

## 5. 输出报告

以 [assets/report-template.html](assets/report-template.html) 为骨架渲染单文件 HTML，默认写到系统临时目录并在回复中给出绝对路径；用户指定路径时写到指定位置。

截图这样进报告：先在报告里写占位符——finding 的标注图用 `__EMBED_<finding id>__`，界面全景图用 `__EMBED_overview:<截图名>__`——再用 `annotate-shot.py --inject <报告路径>` 就地替换成 base64 data URI，保持单文件可转发。它会报告替换数量与内嵌图片数，有缺图或残留占位符时以非零码退出，不要手写替换代码。

报告必须包含：

- 受众与决策结论，作为全篇判定依据。
- 采集到的每个界面的全景截图，以及采集不到的范围和原因。
- 按严重度分组的 findings，每条含原文、类型、为什么该受众不需要、建议文案、位置，以及圈出该文案在真实界面位置的标注截图；未截图的条目写明原因。
- 原文与建议文案的对照。
- 待确认清单。
- 改写后的整页文案全文，供用户直接判断整体效果。

无问题时同样输出报告，状态标为 clean。

## 不变量

- 只读：不修改被审仓库的任何文件，只写报告与截图产物。
- 不发起外部写操作（评论、工单、消息、推送）。采集过程不要为了构造界面状态去触发有副作用的操作——失败登录、提交表单、改配置都不做。
- 截图必须是真实渲染产物。拿不到就记为覆盖范围限制，不用示意图、手绘或源码推断代替。
- 结论只基于实际读到的文案与代码；不可辨认或未定位的内容如实标注，不补全成看似合理的文本。
