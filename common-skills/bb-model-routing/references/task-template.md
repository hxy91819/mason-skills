# 派發任務模板

`bb-dispatch --task` 的正文依此填。模板的目的只有一個：子 agent 拿到的是契約，不是口頭交代。每段都要填，沒有內容就寫「無」。

```markdown
<一句話目標：做什麼、做到什麼程度、不做什麼>

## 先讀
<開工前必讀的檔案與規則，按閱讀順序；含專案 AGENTS.md、相關 skill、來源證據>

## 開工前
- 先 git fetch，確認 HEAD 包含 origin/main；落後就先保全他人未提交檔案（patch 或本機 commit，不用 stash），再 --ff-only 快進，失敗就停。
- 列出工作區裡不屬於本任務的未提交檔案，全程不碰、不一起 commit。

## 授權範圍與根因位置
- 可改的檔案或模組：<清單>
- 若根因落在範圍之外（例如權限判斷在 store 而不在畫面），<允許改／先回報再改>。
- 不做：<明確排除的事，例如不改資料模型、不加頁面、不發新版本>

## 要做
<逐條，具體到元件或檔案；每條可檢查>

## 自行引入的決定
- 任務沒寫明、但實作必須二選一的地方，選不擴大範圍的那個；
- 每個這樣的決定在最終回覆裡單列一段「我自行引入的決定」：決定、理由、影響，讓父線程逐條確認，不得只寫在程式註解或散在正文。

## 交付與驗證
- 驗證方式：<本機如何實際操作或執行；需要截圖的畫面與身分；檢查命令>
- 發布／提交：<是否發布、commit 訊息前綴、是否 push、只 add 自己改的檔案>
- 臨時腳本與產物放哪、交付前是否刪除。

## 回覆格式
1. 版本或 commit
2. 每條「要做」的改法與驗證結果
3. 我自行引入的決定（單列）
4. 與既有文件衝突的地方（只列，不自行改文件）
5. 未完成項
```

使用規則：

- 任務文字只放目標、範圍、輸入與驗收；provider、模型、推理級別不寫進去。
- 「先讀」要含名詞權威來源（術語表、選項檔、狀態清單），實作只引用不另起名；名詞沒定稿就先定稿再派。
- 多個子線程改同一倉庫時，在「開工前」寫明哪些檔案由父線程改，子線程改檔前先拉最新。
- 回覆格式第 3 項是父線程彙總決策的輸入，缺它就退回補。
