# BB task dispatch

<!-- Trigger conditions live only in the description to avoid maintaining them twice. -->

## Dispatch entry

When the agent decides on its own to use a subagent, or the user only asks to "check it with a subagent", use the host's default mechanism. Viewing or continuing an existing thread uses the existing context.

Call `bb-dispatch` for tasks the user has already requested. Tool aliases, models, reasoning levels, and environment mappings follow the user configuration. Before dispatching, confirm the configuration file exists; when `bb-dispatch` reports `cannot read config <path>`, also check that path first: only if the file truly does not exist, enter bootstrap — follow [First-time configuration bootstrap](references/bootstrap.md), reporting progress as you go while detecting available providers and models, propose a configuration, write it after user confirmation, verify with dry-run, then return to dispatching. If the file exists but cannot be read, the configuration is corrupt: report and repair it, do not create a new one over it. Read [Configuration and dispatch](references/dispatch.md) when adjusting existing mappings. For parameter details see `bb-dispatch --help`.

The default skill-manifest-sync install puts the command in `~/.local/bin`. If the current host's `PATH` omits that directory, run the commands below as
`PATH="$HOME/.local/bin:$PATH" bb-dispatch ...`. When only this skill directory is installed, run `scripts/bb-dispatch` under the skill root the host loaded. The command requires Python 3.10+, PyYAML, and `bb` findable on `PATH`.

## Judgment and invocation

Grade each task individually; within the same batch, judge each one separately.

- **`complex`**: Oracle or Judge role; or the parent thread cannot say which system the problem lies in, cannot list candidate approaches, and the task spans multiple systems.
- **`medium`**: passing tests does not mean it is done right, e.g. concurrency, locking and crash recovery, changes to tenant or security isolation boundaries, issuing a "ready to ship/sign off" verdict, or being the sole reviewer the workflow requires with no second reviewer or CI as a backstop; or the parent thread cannot write acceptance criteria.
- **`simple`**: the change, scope, and acceptance are all clear; getting it wrong is cheap and easy to notice.

No need to try a lower tier first. When rework is expensive (on the critical path, errors have external impact, or rework would take hours), go straight to the tier that can get it right in one pass. When a prior thread failed or needed rework, re-grade based on the failure reason, crossing tiers if needed, and record it in the ledger with `--escalate-from <prior-thread-ID>`. When the user names a tier, use it. `--unknown` is optional; record the grading reason in one sentence.

The user can configure the minimum difficulty for work threads in `projects.<BB-project-ID>.min_difficulty`. Review threads pass `--purpose review` to be exempt from the project floor and are routed by the requested difficulty. See [Configuration and dispatch](references/dispatch.md#project-minimum-difficulty).

```bash
bb-dispatch --difficulty simple --task 'Verify the login flow against the existing cases in tests/; fix failures until they pass'
bb-dispatch --difficulty medium --task 'Change the tenant isolation boundary; passing tests is not enough to prove there is no leak'
bb-dispatch --difficulty complex --escalate-from thr_xxx --task '<why the prior thread failed and what the redo requires>'
```

Fill `--task` per the [dispatch task template](references/task-template.md): goal, Read first, Before starting (sync with remote), Authorized scope and root-cause location, Decisions I introduced (must be listed separately), Delivery and verification, Reply format. `--task` contains only the task goal, scope, inputs, and acceptance requirements. Provider, model, reasoning level, and availability checks are dispatch metadata: `bb-dispatch` decides them from configuration and catalogs; they are not written into the child-thread prompt, and the child agent is not asked to re-query or confirm them before starting. When the user explicitly asks to change provider or model, adjust the user configuration and then dispatch; still do not carry routing requirements into `--task`.

Each dispatch selects candidates by `defaults.<difficulty>`; the parent agent only chooses task difficulty, and provider and model are determined by user configuration. The script does not accept `--agent`, and existing tool context is not an exception for bypassing configuration. Pass `--reasoning` only when the user explicitly specifies a reasoning level; otherwise the script reads configuration. When configuration does not specify it, omit the parameter and use the provider default. `fast` follows user configuration only (defaults to `false` when omitted; can be set at top level or per account in `agents.<alias>.fast`; when a cycle is near reset or a temporary burst is needed, add `force_fast: true` in configuration to force it on and exempt it from the patrol circuit breaker); a human editing the file toggles the Fast service tier; the script provides no command-line override. Use `--dry-run` to preview; environment and model validation already done by the script need not be re-queried.

## Dispatch boundaries

All providers, models, reasoning levels, Fast service tier, and default routes come from user configuration; the script performs the corresponding catalog validation before creation. The parent agent is only responsible for choosing task difficulty and must not delegate routing choice or secondary validation to the child agent. When configuration is missing, go through bootstrap first and dispatch only after dry-run passes for all three tiers.

`defaults.<difficulty>` uses fallback by default: a single alias is a fixed choice; an ordered alias chain is validated in order and the first available candidate is dispatched. To spread independent tasks, configure `mode: load-balance`; to spread by quota ratio, configure `mode: weighted-load-balance` and write `candidates` as an "alias: non-negative weight" mapping. `0` pauses that candidate — both sampling and fallback skip it; keep at least one positive-weight candidate. The script orders candidates with a stable hash of difficulty and full task text, maintains no shared counter, and the same task reproduces the same selection and fallback order. Each candidate resolves its own `routes` only by this difficulty or an explicit `default`; candidates lacking both are skipped. When all candidates are unavailable, errors from each are aggregated in the report; after spawn is issued there is no retry, a candidate whose spawn failed is cooled immediately, and after confirming no thread was created, rerunning the same command moves to the next candidate. Exact format and load-balance continuation constraints are in [Configuration and dispatch](references/dispatch.md).

Each dispatch is already an independent BB session; load balancing does not split session context. Do not go out of your way to avoid prefix caching; but do not assume cache is shared across different providers or models either.

Permissions are resolved from user configuration; when native Codex has no permission specified, prefer Approve for me (`auto`); override order is in [Configuration and dispatch](references/dispatch.md). When configuration is missing or validation fails, state the gap; do not silently switch models or escalate permissions.

The script prefixes the dispatch title by difficulty and account: colour represents difficulty (green = simple / yellow = medium / red = complex), shape represents account (circle = main account / square = L account / heart = B account / book = M account); pass `--title` when you need a short title, otherwise it is truncated from the task text.

Report thread ID, actual selection, and status from the returned result; the thread ID is in `result.thread.id` or `result.id` (two known receipt shapes) — take the former first, fall back to the latter if missing. When looking up a thread by title, use substring matching, since titles carry the prefix above. When fallback happens, state the failure reasons along the chain and the actual candidate. Successful creation does not mean the task is done; when the creation result is unclear, query threads first to avoid duplicate dispatch.

## Waiting and concurrency

To limit the number of concurrently running threads for a provider, configure `max_concurrency` in the corresponding `agents.<alias>`. The script shares slots per provider across difficulties and local dispatch processes; `concurrency_models` can specify the set of models sharing the cap, models outside it are unlimited. When full, it falls back within the same tier; when all are full it exits explicitly; when the creation result is unclear it keeps the reservation. Archived threads do not occupy slots; unarchived `error` threads whose only queued messages are waiting for retry and that explicitly have no pending interactions do not occupy slots; running threads and pending interactions are still counted conservatively. Configuration, status queries, recovery, and limit scope are in [the concurrency limits section of Configuration and dispatch](references/dispatch.md#provider-concurrency-limits).

Waiting is driven by BB notifications, not polling. When a child thread's turn completes, fails, or is interrupted, BB delivers a system notification to the parent thread (queued while the parent is busy, delivered as a new turn when idle, containing a summary of the child thread's final output); when a child thread is stuck on a pending interaction there is a separate help notification. When dispatching from inside a BB thread, the script automatically links the current parent thread, keeping the link across environments and projects, and notifications return to the parent along this link. The user may talk directly in a child thread and change its authorization or direction; the notification marks whether the turn was initiated directly by the user, in which case the user's instructions to the child thread take precedence — do not issue corrections, stops, or redispatches based on it unless the user asks. After dispatching, end the current turn or switch to other work; read results and decide next steps when the notification arrives. `bb thread wait` loops, repeated `show`, or re-querying after sleep are all redundant polling; query once only when immediate confirmation is needed, e.g. the creation result is unknown.

Every intermediate message from a child thread wakes or interrupts the parent, so when linking a parent thread the script appends a fixed reporting section `## How to report (appended by bb-dispatch)` to the end of the task: progress, interim findings, and newly created resources are held until the end of the turn and reported once as the task requires; facts that need an immediate record are written to a workspace file. When the task genuinely needs intermediate reports, state it in `--task`; the task body takes precedence. A task copied back from a child's first message (e.g. for redispatch) has this section stripped before it is reattached; the legacy Chinese heading written by earlier versions is stripped too. When a child thread still sends a progress-only intermediate message (`[bb message from thread:…]`, not a completion notification), do not reply or restate it; end the turn in one sentence and handle its facts together with the final reply. When the same child thread keeps sending them, remind it once with `bb thread tell`.

Long tasks (waiting for CI, waiting for review, executing in multiple batches) wake the parent at the end of every turn. Dispatch such tasks with `--parent-notifications stuck` (or write `parent_notifications: stuck` at the top level of configuration): BB only auto-wakes the parent when the child thread fails, is interrupted, or awaits approval, and the script instead appends a reporting section saying "only `bb thread tell` the parent when approval is needed, a decision is needed or you are stuck, a stage is complete, or an out-of-scope problem is found". Stalls are still discovered by the parent's reconciliation, not by per-turn notifications.

When a child thread errors due to provider unavailability, quota exhaustion, or session error, run `bb-dispatch --on-failure <thread-ID>`. When it returns `waiting` or `retry-scheduled`, wait for the notification; if it errors again, rerun the command. When it returns `not-failed`, wait as usual. When it returns `cooled`, run `bb-dispatch --redispatch <thread-ID>` to switch candidates; the script recovers the original purpose, requested difficulty and task text from the ledger and first-turn log and records the prior thread. If there is partial output, after the new thread is created use `bb thread tell` to supply progress and locations. When BB's automatic retry waits too long, first cancel with `bb provider-retry cancel <thread-ID>`, then record failure with `--record-outcome <thread-ID> --outcome failed` and redispatch. Rejected tasks, normal completion, or pending interactions are handled per their own status. If the same task still fails after switching candidates, report it. Retry and cooldown rules are in [Configuration and dispatch](references/dispatch.md#dispatch-and-configuration-rules).

Before parallelizing, split by task nature:

- Read-only tasks (research, review, search, verification) do not change shared state and can be dispatched back-to-back and run in parallel.
- For write tasks, check dependencies first: when a later task consumes an earlier task's output, dispatch serially in dependency order, waiting for the earlier one's completion notification before dispatching the next; only write tasks that are mutually independent with non-overlapping write targets run in parallel.

When concurrent writes may produce modification conflicts, isolate with `use-worktree`; when there is no conflict, use the current environment. Check branch, workspace, and worktrees before operating, and respect user authorization. Once an isolated worktree is ready, its directory path can be passed to `--environment` and BB creates an attached environment. A child thread's environment directory must stay intact during the turn: when using the current environment it is the parent thread's working tree; even a directory prepared specifically for the child thread, if deleted during the turn, makes the turn error and the final reply never reaches the parent. The task brief therefore states: to switch branches, create a separate worktree, which the child thread cleans up itself; a dedicated environment directory is cleaned up after the parent receives the reply.

## As an orchestration backend

The deterministic driver of `large-task-orchestrator` dispatches Workers, Validators, and (on exceptions) Judges through `bb-dispatch`: Workers map
capability tier to `--difficulty`, Validators are fixed at `--difficulty simple`, Judges are fixed at `--difficulty complex`.
The driver passes only task text, difficulty, and existing environment; routing is still determined by this configuration. For the state machine and wait/output/tell compatibility see
`references/bb-dispatch-loop.md` of the owning `$large-task-orchestrator`; when that contract is needed the host loads the target Skill, do not read it by sibling path. The driver is a script state machine,
blocking with `bb thread wait` and handling stalls itself, independent of the in-session parent agent's notification path.

All three thread types use only `simple`, `medium`, `complex` difficulty routes. `agents.<alias>.routes` configures model and reasoning per difficulty and a `default` entry; selection rules are in [Configuration and dispatch](references/dispatch.md).

## Observability

The script maintains a run ledger and circuit-breaker cooldown table at the local Git-ignored path `~/.cache/bb-dispatch/ledger.json` (overridable with `--ledger` or `BB_DISPATCH_LEDGER_PATH`); read/write errors warn on the side and never block the main dispatch:

1. **Minimal facts and rolling rollup**: each dispatch records only `id`, `ts`, `project`, `parent_thread`, `purpose`, `difficulty`, `requested_difficulty`, `agent`, `provider`, `model`, `reasoning`, `task_chars`, `outcome`, `outcome_ts`, `retries`, `retry_ts`; when provided it also records `unknown` (truncated to 120 characters) and `escalated_from`; quota failures also record `quota: true`. Task body, diff, error text, and thread logs are not stored. The live window keeps the most recent 200 entries; entries within 48 hours are still needed to detect terminal states and compute cooldowns and are kept even beyond that; older overflow is automatically rolled up into fixed-dimension `rollups`, and live and rollup never double-count. Ledger read-modify-write uses a file lock and re-reads and merges before writing, so parallel dispatches and write-backs do not overwrite each other.
2. **Two-layer backoff circuit-breaker cooldown (Circuit Breaker)**: failures whose type cannot be determined do not read error text. The original-session layer is handled by `--on-failure`: when a retry is already queued it does not intervene; otherwise it retries in the original session at 1, 2, 4 minutes, and only after these are exhausted (or BB has retried to its limit) records `failed`. Structured quota signals record `failed` directly with `quota`, skipping these three retries; which signals count is in [Configuration and dispatch](references/dispatch.md). Erroring again after a success restarts the count. The dispatch layer cools per provider and model, looking only at terminal states within 48 hours: a normal failure first cools for 15 minutes, a quota failure first for 1 hour; failures during cooldown only extend it, failing again after cooldown ends doubles it, up to 6 hours. When the subscription window gives a later reset time, cool until that moment, which can exceed 6 hours. One success resets to zero. As soon as one quota failure exists for a provider and model, subsequent dispatches skip it, without waiting for each thread to fail on its own. Each dispatch first reads `bb thread list` once and marks as `completed` threads within 48 hours that are still awaiting a result (still recorded as `spawned`, or that succeeded and are retrying in the original session) and are idle with no queued messages and no pending interactions; if it cannot read, it warns and skips. Candidates whose spawn failed and those skipped by `--fallback-from` are additionally cooled for 15 minutes. Cooling candidates are skipped first; when all are cooling, one is still tried to avoid deadlock. When a terminal state is wrong, or an abandoned task must be recorded as failed, correct it by stable thread ID (unknown IDs are rejected with an error; repeated write-back overwrites):
   ```bash
   bb-dispatch --on-failure <thread-ID>
   bb-dispatch --record-outcome <thread-ID> --outcome failed
   ```
3. **Aggregate review**: run `bb-dispatch --history-summary` (or `--stats`) for read-only output (it likewise first fills in terminal states from thread status, but does not write the ledger) of difficulty share, per-candidate failure rates, currently active cooldowns, and deterministic review hooks (`high_failure_rate` when a candidate has at least 3 dispatches and failure rate $\ge 30\%$). At dispatch time `selection.warnings` carries these hooks and each is also written to stderr, so they are visible even when only the stdout thread ID is consumed.
4. **Review log**: `ledger.events.jsonl` next to the ledger is append-only for five event types: `dispatch` (with the ledger entry's minimal facts: purpose, parent thread, reasoning level, `task_chars`, `unknown`, `escalated_from`, plus requested difficulty when raised by a project floor; `diverted` is candidates bypassed due to cooldown, `quota_diverted` is the count of those skipped due to quota cooldown), `deferred` (handed to BB automatic retry), `retry`, `recovered`, `cooled` (with reason and level). It stores no task body; beyond 4 MB the older half is dropped. The `retry_review` in `--history-summary` summarizes the last 7 days: counts, `retry_recovery_rate` (share of faults retried in the original session that eventually recovered), and distributions by count, reason, provider and model, and date; `quota_cooldown_skips` is the number of times a candidate was skipped due to quota cooldown. Use it to judge whether retries work, whether cooldowns are frequent, and whether trends are normal.
5. **Delivery quality**: the parent thread does not self-assess acceptance. `bb-dispatch --followups [--days 7]` lists, read-only, every thread dispatched in the last few days: title, whether it delivered normally (a manually stopped turn does not count as delivery and is recorded as `stopped_before_delivery`), threads redispatched with `--escalate-from` (`redispatched_as`), and messages appended by the parent thread or user after first delivery (excluding `[bb_long_task]` and `[bb system]` notifications), summarized per candidate. Bodies appear only in the output, taken from BB thread records, and never enter the ledger; the review log is kept about a month, longer than the live window, and is authoritative for cross-day analysis. Appended messages mix rework, next tasks, verdicts, and progress syncs; the script does not classify them. In the weekly review the model classifies each one, splitting rework into "model problem" (omissions, stopping early, doing it wrong, harmful operations) and "requirement change"; redispatching after a stop also counts as rework; also spot-check threads with no appended messages, since no follow-up does not mean it was done right. Gaps: classification relies on model judgment with no stable deterministic metric; `simple`-tier output is rarely reviewed independently, so rework is easily underestimated; 7 days takes about 5 minutes (reading thread logs one by one).
