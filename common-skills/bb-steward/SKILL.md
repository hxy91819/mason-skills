# BB 管家

这是流程类 Skill，仅在用户显式调用 `$bb-steward` 时进入。管家是会话里的编排者：自己决定下一步、把具体工作派给
BB 子线程、收通知后汇总，并把跨会话必须保留的信息写进工作簿。

分工是判断留下，调研和体力活派出。要懂用户意图和来龙去脉才能做对的判断（范围、归属、取舍、做到什么程度）由管家
自己做。判断要用的事实，几条命令能查完的管家自己查；要大量阅读或排查的，例如读代码和文档、上服务器翻日志找 bug
线索、收集舆情和外部信息，派只读调研线程：只给问题、不附管家的猜测，要它带证据交回事实和可能原因，不替管家定怎么做，
不改东西。代码和文档改动、长时间运行、可并行的独立任务、独立审查和经手秘密的工作也
派出去。每转一手都会丢细节，子线程摘要里的错误又和正确结论写得一样笃定，所以判断不外包，验收不只看摘要。

开始前加载 `$bb-model-routing`，派发、难度归类、任务模板和等待规则全部以它为准，本 Skill 不重复。管家会话长，
上下文压缩后的第一次派发前重读它的「判断与调用」。按上文分工留给子线程的调研和探索，就是它所说的“保留不确定性”，
归 `medium`。

## 与 large-task 的分工

管家处理"跨会话、但不值得拆 Story"的目标：人在环路，Agent 自己拿主意，没有脚本状态机。目标大到需要 Story
拆分、无人值守连续执行时，转 `$large-task-planning` 建计划，再由 `$large-task-orchestrator` 执行；工作簿的路线
进 SPEC 的交付路线，关键决策进 SPEC 的已定取舍，用户待办进 STATUS 的需要关注，然后删除工作簿。两套不并存。

## 工作簿

每个目标一份，提交进目标仓库，默认路径 `docs/steward/<topic>.md`；项目 `AGENTS.md` 另有指定时以项目为准。
工作簿、项目 `AGENTS.md` 里指向它的那一行（"存在时先读"）以及项目文档索引的登记，都算工作簿本身，由管家
直接写并按项目约定提交，不派子线程；它们让不经本 Skill 进入的会话也能接上。其余改动仍派出去。子线程只在
"先读"里读工作簿。格式见[工作簿模板](references/workbook-template.md)。

工作簿只有三段，各自的准入判据：

- **路线**：阶段清单和当前位置，一个阶段一行，未完成行末尾用 `←` 标状态，取值见「收尾对账」。一行里有能
  分头推进的事项就拆行；用户提过、跨回合还没收口的要求也按阶段进路线。项目已有路线图（issue、计划文档）
  时只放链接和当前位置，不复制阶段。任务清单、"做了什么"、子任务矩阵、实时配额计数和中间 commit SHA
  不进这里，那是项目 Issue、派发文本和 git log 的事。
- **关键决策**：两条同时成立才记：下个会话不知道这条就很可能重做或翻案；从代码、git、既有文档推不出来。一条
  一行，写决定、日期、原因、影响范围。新决定覆盖或收窄旧决定时，直接原地更新该行，不按时间流水账追加互相冲突的
  旧条目。项目已有决策登记制度（决策地图、ADR）时只放链接，这段剩下的通常只有管家与用户之间的操作约定，例如
  哪些事用户亲自裁决、合并前固定派什么审查。子线程回复里"自行引入的决定"逐条过这个判据，绝大多数随线程消亡。
  用户决策会越积越多，这段只留仍约束未完成工作或日常操作的条目：所影响阶段全部完成、或已写进项目文档/ADR
  的条目移出（要求帐保留原话与结果）。条数超过建议值只是提醒，不为凑数删掉仍有约束力的用户决策；一屏行数才是硬上限。
- **用户待办**：只有用户本人能做的事，每条写做什么、为什么只能用户做、挡住了哪个阶段、提出日期、状态。
  "为什么只能用户做"以类别开头：`凭据账号`、`真机线下`、`对外沟通`、`不可逆上线`、`用户保留`（用户明确
  说过由自己定）；归不进这五类的事由管家推进，见「等待用户时继续推进」。不挡任何阶段的事"挡住"栏写
  "不挡"，排在挡阶段的后面。待办只有待办和已完成两种状态；用户说做完或管家验证到即改为已完成，保留原行。

工作簿是人读的状态页，不是实时运行日志。只在阶段完成、路线调整（含 `←` 后的状态、定时时间、依赖对象变化）、关键决策变更或用户待办状态变更时更新并提交工作簿；
同一行换了线程 ID 只改行内文字、不单独提交，中途进度、配额消耗计数不进工作簿。每次修改工作簿后运行确定性门禁校验结构与一屏容量（三段标题固定、非空行 $\le 45$、单行可见字符 $\le 180$、路线禁塞表格）：

```bash
python3 scripts/steward_workbook.py --mode check --file <工作簿路径>
python3 scripts/steward_workbook.py --mode should-commit --file <工作簿路径>
```

容量或结构报错时按准入判据删减；要求帐入口报错时补齐链接目标。`--mode should-commit` 返回 `should_commit: false` 时说明仅有线程 ID 或括号内描述调整，不单独生成 git commit。

## 要求帐

每个目标另建 `docs/steward/<topic>-要求帳.md`，工作簿标头用一句话链接过去。要求帐及此链接由管家直接维护、按项目约定提交；
不受工作簿一屏容量限制，三段结构不变。格式与示例见[工作簿模板](references/workbook-template.md)。

准入是用户交代过的每件事，包括调研、实现、操作约定、补充与纠正；一条消息含多个独立要求就拆行。
收到要求先以「進行中」新增一列，再推进；状态变化时原地更新，保留旧列，不搬走或删除。接手既有目标时从可读取的
上下文、交付材料与既有记录补齐历史要求；无法查证的结果写明缺口，不猜成完成。

按时期分节（`## <起始日> 起（主题）`），每节一张 `| 日期 | 要求 | 狀態 | 結果 | 材料 |` 表。
状态只用下面七种字面值（项目用简体写正文时也保留这些状态值与表头）：

| 状态 | 含义与结果要求 |
| --- | --- |
| 完成 | 要求的交付已验收；结果写实际产出与效果 |
| 採納 | 建议或约定已接受并落实到相应规则；写落在哪里 |
| 部分採納 | 写清接受与未接受的范围、剩余部分的去向 |
| 進行中 | 正在推进；写当前进展或依赖 |
| 待使用者 | 下一步需要用户行动或裁决；写具体问题，对应工作簿用户待办 |
| 被覆蓋 | 后续要求替代了本项；结果写被哪一列或哪件事取代 |
| 排除 | 不再推进；结果写原因 |

完成／採納的材料要有可定位的链接、文件地址、commit、PR，或明确写「會話回覆」（可附日期）。结果写可量化的
结论，例如「CI 21→8 分（-62%）」；无法量化的写具体变化与范围，不用「已完成」代替结果。材料链接应直接可打开，
本机材料标明适用范围，临时预览标明有效期；脚本只检查材料形式，不证明材料可访问或结论真实。

工作簿三段仍分别回答接下来走哪、哪些取舍要记住、哪些事只能用户做；要求帐回答每项要求的状态、结果与材料。
用户问总结或「要我决策的有哪些」时，先逐项对帐：核对待使用者项，也核对已交付但尚待用户选择的调研建议，避免
把「调研完成」误当成「建议已裁决」；将待裁决事项另记对应要求与用户待办。平台管家入口可用时，回复不再重复附工作簿链接；登记输出 `plugin.status` 为 `skipped` 时仍附入口，用户可从标头查全帐。

既有 Markdown 历史流水账经用户确认沿用时，标头精确标为 `[要求帐（历史流水账）](相对索引.md)`，保留旧账和索引链接，不改写成五列表或编造状态统计。平台可查看索引及其相对账目链接，明确标示标准统计不适用；标准要求帐仍须通过下列校验。标头没有要求帐入口即是待补缺口，不能凭结构检查结果宣称入口齐全。

每次更新要求帐后运行（其状态变化单独构成提交理由，不受工作簿 `should-commit` 节流影响）：

```bash
python3 scripts/steward_workbook.py --mode ledger-check --file <要求帐路径>
```

## 会话开始

1. 读工作簿及标头链接的要求帐；缺要求帐时按上节补建并链接。读 `bb status`，检查分支、`git status --short`、`git worktree list`。没有工作簿时先建：从
   `bb status` 的子线程、当前会话上下文、git log 和项目既有计划恢复路线位置和已埋的用户待办，再继续。
2. 登记看门狗（见「看门狗」）；脚本自动同步管家插件标记、工作簿与要求帐入口，无须管家另行调用插件。插件未安装或暂未就绪只在登记输出标注跳过，不影响看门狗；解除失败会保存待同步操作，由后续看门狗运行重试。文件移动后重新登记。Git-ref 模式同步 repo/ref/相对路径到平台入口，后续同线程重登记沿用来源，不解除绑定。同线程重登记只更新，别的线程登记着同工作簿时即接任，按「接任」补齐上下文。
3. 从路线的当前位置决定下一步；遇到用户依赖时按下节处理。

## 接任

会话故障或模型降级后，用户会新开线程让你接手。「会话开始」第 2 步的登记就完成交接：看门狗把这份工作簿的
登记换成你，把旧管家在跑、刚结束和「进行中」引用的子线程转到你名下，撤掉旧线程排队的自动重试，并通知旧线程
停手。登记输出 `handovers` 里有失败的步骤，手动补上。

然后读 `bb thread log <旧线程> --limit 3`，把用户提过、还没进工作簿的要求补进路线；关键决策原地更新一行
`管家：thr_新（MM-DD 接任 thr_旧）`，按「工作簿」提交。

收到 `[bb-steward 交接]` 说明你已被接任：停止派发和改工作簿，用户来找时指向新线程，不用回复。

## 等待用户时继续推进

能从现有上下文、已定决策或只读核实中解决的问题，由管家先处理。可逆、在已授权范围内、有推荐做法的事直接按推荐做，
回复里说明做了什么、怎么撤回，不写成待办等用户。确实只有用户能决定的，记入工作簿的“用户待办”，
写清问题和受阻阶段；只暂停依赖该答案的分支，继续其他已授权工作、接收子线程回报和处理子线程求助。

普通澄清通过工作簿和普通回复提出，按用户规则把待决定的选项放在回复最后，再结束当前回合，让后续子线程通知能重新
唤醒管家。同步提问工具（如 `AskUserQuestion`）会挂起整个会话，使子线程通知只能排队，因此普通澄清不用这类工具。
真正要求暂停执行的授权或审批仍按原有规则等待；缺少答案的分支不擅自执行。

只有所有当前可推进的分支都依赖用户时，才报告整体等待；仍用普通回复结束回合，保留接收后续回报和求助的能力。

## 推进循环

1. 收到用户要求，按「先回复、再下发、后记账」的顺序处理：
   - **先回复**：只核实回答所依赖的事实，核实力度与后果相称——解释类问题查清关键事实即可；动作和决策查到足以下结论为止。核实够了就立刻回复用户，回复写在派发、记账和提交之前，后面的工具调用不推迟它。
   - **再下发**：派发前核实决定任务范围的事实（归属、现网或环境实况、用户原意），任务里写核实过的事实，不写推测；需要大量阅读才能核实的，先按上文派只读调研线程。实现细节留给子线程，管家不在主会话预查具体代码行，也不代为大段拉取数据落盘。再按 `$bb-model-routing` 的任务模板与分档标准构造并派发下一步任务，“先读”包含工作簿路径。
   - **后记账**：按「要求帐」记一列，按第 4 步更新工作簿，再按「收尾对账」结束回合，等 BB 通知。
2. 收到完成通知或阻塞求裁决通知后，只读通知摘要、子线程最终回复和它的 git 改动，不读子线程全文；强模型会话的上下文留给判断，不装子线程产物。结果是用户会直接碰到的（环境、配置、云资源、对外入口），先用只读命令核一次实况再验收、再报告。子线程完成后，更新对应要求列的状态、具体结果与材料；未验收的部分保留进行中。
3. 逐条处理“自行引入的决定”：进工作簿、接受但不记、退回重做三选一；通过 `bb-dispatch --record-decision <线程ID> --decision ...` 回写裁决（终态由脚本自动记录，有误时再加 `--outcome` 改正）。用户事后纠正的问题能追溯到某次派发时，把该线程改记为 `--decision reworked`（覆盖原裁决），让 `--history-summary` 的接受率反映转手丢掉的部分。
4. 阶段收口、路线状态变化、决策变更或新冒出用户待办时，更新工作簿，运行 `scripts/steward_workbook.py --mode should-commit --file <工作簿路径>` 通过且确认 `should_commit: true` 后提交。
5. 阶段完成后继续下一条可推进的路线；用户依赖按“等待用户时继续推进”处理。

## 收尾对账

每个回合在回复用户之后、结束之前对一遍账：路线里每个未完成行落在下面一种状态，写在该行 `←` 之后。

- `进行中 thr_xxx`：有线程正在做这件事，行里写出它的线程 ID。
- `等用户`：有未完成的用户待办，"挡住"栏写着这一行的阶段编号（行没有编号时写标题）。
- `定时 MM-DD HH:MM <做什么>`：已经排定时间的动作，如 automation、提醒、窗口。
- `排在 <事项> 后：<依赖的产出>`：要消费前一项的产出，或和它写同一目标；前一项完成，这一行就该推进。

落不进这四种的行（包括"随后""暂缓""远景"）当场派出去；用户明确说先不做的，从路线删去、记进关键决策。
状态有变化就按「工作簿」提交，然后跑对账检查，退出码 0 再结束回合；退出码 2 时按输出逐项处理：

```bash
python3 scripts/steward_workbook.py --mode reconcile --live --file <工作簿路径>
```

`--live` 经 `bb thread list` 核对 `进行中` 的线程：在跑、有排队消息、有后台活动或结束不到 30 分钟算活着。

## 看门狗

`scripts/steward_watch.py` 由 BB 脚本 automation 每 30 分钟跑一次，不调模型：管家回合失败且没有排队的重试时
替它重试，恢复后提醒核对失败期间的通知；管家空闲而对账不过时，把问题行发给管家；管家的模型变了（BB 请求的
模型或推理级别，或 Claude Code 实际回复用的模型）时提醒一次。节流和升级规则见脚本 `--help`。会话开始时登记，
首次登记会在当前项目创建 automation：

```bash
python3 scripts/steward_watch.py register --workbook <工作簿路径> [--ref origin/<分支>] [--name <简称>]
```

工作簿以远端分支为准、主工作区不在该分支时传 `--ref`。插件与 watcher 保留原线程和主机归属，Git 的远端/分支也是同目标匹配的一部分；新线程接任 Git 目标须显式传相同 `--ref`。同线程重登记不传时沿用原 ref。
每次主动打开/刷新 Git 入口先核远端并固定 SHA，工作簿、帐目及相对链接按同 SHA 读取；磁盘无文件也可使用。远端不可达、ref 删除或超时会明确报不能核实，不回退旧本地 ref。相对链接继续使用本次 SHA；历史索引中的目录链接（如 `2026-10/`）由插件列出目录项，再导航到原分片，保留原索引和原文。“刷新远端文档”才重新核远端。正文仅在插件中只读展示，不生成持久工作簿副本。大文档与目录分页显示，未读完时明确标示并提供继续按钮，续页仍固定同 SHA。
通过插件 CLI/RPC 读取时，`document` 默认返回第一页及 `next: {path, sha, offset}` 或 `null`。完整续读参数、文件 UTF-8 字节/目录条目 offset 单位及 1 MiB CLI 输出边界见插件自带 steward skill；需要诊断或导出正文时按名称加载它，使用实际返回的 next 续读，不自行把部分正文当完整内容。
Git 来源的确定性检查使用 `python3 scripts/steward_workbook.py --mode check --repo <仓库绝对路径> --ref origin/<分支> --file <仓库相对路径>`；`ledger-check` 同样支持。一次操作已固定 SHA 时用 `--revision <40位SHA>` 代替 `--ref`，输出 snapshot 明示该版本，不声称最新。Git 来源不支持 `should-commit`，提交判断仍针对实际编辑的本地工作簿。历史流水账的 `ledger-check --ledger-kind history` 返回不适用、没有标准统计；标准帐保留默认校验。收到 `[bb-steward 看门狗]` 消息就按「收尾对账」
处理，不用回复它。消息要你告诉用户的（模型变了、同一问题催满 2 次、长时间中断后恢复），在本回合回复里说明
变化或问题和影响；模型变了时给出选项：换回原模型，或新开线程接任。

## 回看

运行事实在 BB 线程记录与 `bb-dispatch` 本地账本里：`bb thread show <线程ID>` 看单次派发结果，`bb thread list` 看本会话派出的线程，`bb-dispatch --history-summary` 看难度分布、候选成功率/接受率、原会话重试与冷却走势和复盘提示，`scripts/steward_workbook.py --mode check --file <工作簿路径>` 检查工作簿健康度。工作簿不存线程 ID 以外的运行细节。

看门狗的记录在它自己的事件日志里：`scripts/steward_watch.py report --since <分钟>` 看各管家最近的检查、催办、接任、模型变化和需要用户看一眼的事，`scripts/steward_watch.py summary` 看 7 天内的催办后解决率、重试、失败、接任与模型变化次数和复盘提示。日志超过 2 MB 丢掉较早的一半，不做长期折算。
