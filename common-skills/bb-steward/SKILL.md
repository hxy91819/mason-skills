# BB 管家

这是流程类 Skill，仅在用户显式调用 `$bb-steward` 时进入。管家是会话里的编排者：自己决定下一步、把具体工作派给
BB 子线程、收通知后汇总，并把跨会话必须保留的信息写进工作簿。管家本人只读、只判断、只写工作簿；代码和文档改动
一律派出去。

开始前加载 `$bb-model-routing`，派发、难度归类、任务模板和等待规则全部以它为准，本 Skill 不重复。

## 与 large-task 的分工

管家处理"跨会话、但不值得拆 Story"的目标：人在环路，Agent 自己拿主意，没有脚本状态机。目标大到需要 Story
拆分、无人值守连续执行时，转 `$large-task-planning` 建计划，再由 `$large-task-orchestrator` 执行；工作簿的路线
进 SPEC 的交付路线，关键决策进 SPEC 的已定取舍，用户待办进 STATUS 的需要关注，然后删除工作簿。两套不并存。

## 工作簿

每个目标一份，提交进目标仓库，默认路径 `docs/steward/<topic>.md`；项目 `AGENTS.md` 另有指定时以项目为准。
工作簿、项目 `AGENTS.md` 里指向它的那一行（"存在时先读"）以及项目文档索引的登记，都算工作簿本身，由管家
直接写并按项目约定提交，不派子线程；它们让不经本 Skill 进入的会话也能接上。其余改动仍派出去。子线程只在
"先读"里读工作簿。格式见[工作簿模板](references/workbook-template.md)。

工作簿只有三段，各自的准入判据：

- **路线**：阶段清单和当前位置，一个阶段一行，标出已完成、进行中、未开始。项目已有路线图（issue、计划文档）
  时只放链接和当前位置，不复制阶段。任务清单、"做了什么"、子任务矩阵、实时配额计数和中间 commit SHA
  不进这里，那是项目 Issue、派发文本和 git log 的事。
- **关键决策**：两条同时成立才记：下个会话不知道这条就很可能重做或翻案；从代码、git、既有文档推不出来。一条
  一行，写决定、日期、原因、影响范围。新决定覆盖或收窄旧决定时，直接原地更新该行，不按时间流水账追加互相冲突的
  旧条目。项目已有决策登记制度（决策地图、ADR）时只放链接，这段剩下的通常只有管家与用户之间的操作约定，例如
  哪些事用户亲自裁决、合并前固定派什么审查。子线程回复里"自行引入的决定"逐条过这个判据，绝大多数随线程消亡。
- **用户待办**：只有用户本人能做的事，每条写做什么、为什么只能用户做、挡住了哪个阶段、提出日期、状态。
  不挡任何阶段的事"挡住"栏写"不挡"，排在挡阶段的后面。待办只有待办和已完成两种状态；用户说做完或管家
  验证到即改为已完成，保留原行。

工作簿是人读的状态页，不是实时运行日志。只在阶段完成、路线调整、关键决策变更或用户待办状态变更时更新并提交工作簿；
子线程启动、中途进度、配额消耗计数不改工作簿。每次修改工作簿后运行确定性门禁校验结构与一屏容量（三段标题固定、非空行 $\le 45$、单行可见字符 $\le 180$、路线禁塞表格）：

```bash
python3 scripts/steward_workbook.py --mode check --file <工作簿路径>
python3 scripts/steward_workbook.py --mode should-commit --file <工作簿路径>
```

一段超过一屏或 `--mode check` 报错就说明准入判据没守住，先删再加；`--mode should-commit` 返回 `should_commit: false` 时说明仅有括号内微状态描述调整，不单独生成 git commit。

## 会话开始

每次给用户回复都附上工作簿的可点击链接，方便查看路线和用户待办；回复中不重复展开工作簿内容。有需要用户决策的事项时，简要点明即可。

1. 读工作簿；读 `bb status`，检查分支、`git status --short`、`git worktree list`。没有工作簿时先建：从
   `bb status` 的子线程、当前会话上下文、git log 和项目既有计划恢复路线位置和已埋的用户待办，再继续。
2. 从路线的当前位置决定下一步。需要用户先做决定的，按用户规则列成编号选项放在最后。

## 推进循环

1. 按 `$bb-model-routing` 的任务模板与分档标准构造并派发下一步任务，“先读”包含工作簿路径；管家不在主会话预查具体代码行或代拉大段数据落盘。派发后结束回合，等 BB 通知。
2. 收到完成通知或阻塞求裁决通知后，只读通知摘要、子线程最终回复和它的 git 改动，不读子线程全文；强模型会话的上下文留给判断，不装子线程产物。
3. 逐条处理“自行引入的决定”：进工作簿、接受但不记、退回重做三选一；通过 `bb-dispatch --record-decision <线程ID> --decision ...` 回写裁决（终态由脚本按线程状态自动记录，有误时再加 `--outcome` 改正）。
4. 阶段收口、决策变更或新冒出用户待办时，更新工作簿，运行 `scripts/steward_workbook.py --mode should-commit --file <工作簿路径>` 通过且确认 `should_commit: true` 后提交。
5. 阶段完成且下一步依赖用户时停下，列编号选项。

## 回看

运行事实在 BB 线程记录与 `bb-dispatch` 本地账本里：`bb thread show <线程ID>` 看单次派发结果，`bb thread list` 看本会话派出的线程，`bb-dispatch --history-summary` 看难度分布、候选成功率/接受率与复盘提示，`scripts/steward_workbook.py --mode check --file <工作簿路径>` 检查工作簿健康度。工作簿不存线程 ID 以外的运行细节；需要时在路线行末附最近一个线程 ID。
