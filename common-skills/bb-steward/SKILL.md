# BB 管家

这是流程类 Skill，仅在用户显式调用 `$bb-steward` 时进入。管家是会话里的编排者：自己决定下一步、把具体工作派给
BB 子线程、收通知后汇总，并把跨会话必须保留的信息写进工作簿。

分工是判断留下，调研和体力活派出。要懂用户意图和来龙去脉才能做对的判断（范围、归属、取舍、做到什么程度）由管家
自己做。判断要用的事实，几条命令能查完的管家自己查；要大量阅读或排查的，例如读代码和文档、上服务器翻日志找 bug
线索、收集舆情和外部信息，派只读调研线程：只给问题、不附管家的猜测，要它带证据交回事实和可能原因，不替管家定怎么做，
不改东西。代码和文档改动、长时间运行、可并行的独立任务、独立审查和经手秘密的工作也
派出去。每转一手都会丢细节，子线程摘要里的错误又和正确结论写得一样笃定，所以判断不外包，验收不只看摘要。

开始前加载 `$bb-model-routing`，派发、难度归类、任务模板和等待规则全部以它为准，本 Skill 不重复。

## 与 large-task 的分工

管家处理"跨会话、但不值得拆 Story"的目标：人在环路，Agent 自己拿主意，没有脚本状态机。目标大到需要 Story
拆分、无人值守连续执行时，转 `$large-task-planning` 建计划，再由 `$large-task-orchestrator` 执行；工作簿的路线
进 SPEC 的交付路线，关键决策进 SPEC 的已定取舍，用户待办进 STATUS 的需要关注，然后删除工作簿。两套不并存。

## 工作簿

每个目标一份，提交进目标仓库，默认路径 `docs/steward/<topic>.md`；项目 `AGENTS.md` 另有指定时以项目为准。
工作簿、项目 `AGENTS.md` 里指向它的那一行（"存在时先读"）以及项目文档索引的登记，都算工作簿本身，由管家
直接写并按项目约定提交，不派子线程；它们让不经本 Skill 进入的会话也能接上。其余改动仍派出去。子线程只在
"先读"里读工作簿。格式见[工作簿模板](references/workbook-template.md)。

工作簿只有三段，各自的准入判据：

- **路线**：阶段清单和当前位置，一个阶段一行，未完成行末尾用 `←` 标状态，取值见「收尾对账」。一行里有能
  分头推进的事项就拆行；用户提过、跨回合还没收口的要求也按阶段进路线。项目已有路线图（issue、计划文档）
  时只放链接和当前位置，不复制阶段。任务清单、"做了什么"、子任务矩阵、实时配额计数和中间 commit SHA
  不进这里，那是项目 Issue、派发文本和 git log 的事。
- **关键决策**：两条同时成立才记：下个会话不知道这条就很可能重做或翻案；从代码、git、既有文档推不出来。一条
  一行，写决定、日期、原因、影响范围。新决定覆盖或收窄旧决定时，直接原地更新该行，不按时间流水账追加互相冲突的
  旧条目。项目已有决策登记制度（决策地图、ADR）时只放链接，这段剩下的通常只有管家与用户之间的操作约定，例如
  哪些事用户亲自裁决、合并前固定派什么审查。子线程回复里"自行引入的决定"逐条过这个判据，绝大多数随线程消亡。
- **用户待办**：只有用户本人能做的事，每条写做什么、为什么只能用户做、挡住了哪个阶段、提出日期、状态。
  "为什么只能用户做"以类别开头：`凭据账号`、`真机线下`、`对外沟通`、`不可逆上线`、`用户保留`（用户明确
  说过由自己定）；归不进这五类的事由管家推进，见「等待用户时继续推进」。不挡任何阶段的事"挡住"栏写
  "不挡"，排在挡阶段的后面。待办只有待办和已完成两种状态；用户说做完或管家验证到即改为已完成，保留原行。

工作簿是人读的状态页，不是实时运行日志。只在阶段完成、路线调整（含 `←` 后的状态、定时时间、依赖对象变化）、关键决策变更或用户待办状态变更时更新并提交工作簿；
同一行换了线程 ID 只改行内文字、不单独提交，中途进度、配额消耗计数不进工作簿。每次修改工作簿后运行确定性门禁校验结构与一屏容量（三段标题固定、非空行 $\le 45$、单行可见字符 $\le 180$、路线禁塞表格）：

```bash
python3 scripts/steward_workbook.py --mode check --file <工作簿路径>
python3 scripts/steward_workbook.py --mode should-commit --file <工作簿路径>
```

一段超过一屏或 `--mode check` 报错就说明准入判据没守住，先删再加；`--mode should-commit` 返回 `should_commit: false` 时说明仅有线程 ID 或括号内描述调整，不单独生成 git commit。

## 会话开始

1. 读工作簿；读 `bb status`，检查分支、`git status --short`、`git worktree list`。没有工作簿时先建：从
   `bb status` 的子线程、当前会话上下文、git log 和项目既有计划恢复路线位置和已埋的用户待办，再继续。
2. 登记看门狗（见「看门狗」）；已登记的重跑只更新登记。
3. 从路线的当前位置决定下一步；遇到用户依赖时按下节处理。

## 等待用户时继续推进

能从现有上下文、已定决策或只读核实中解决的问题，由管家先处理。可逆、在已授权范围内、有推荐做法的事直接按推荐做，
回复里说明做了什么、怎么撤回，不写成待办等用户。确实只有用户能决定的，记入工作簿的“用户待办”，
写清问题和受阻阶段；只暂停依赖该答案的分支，继续其他已授权工作、接收子线程回报和处理子线程求助。

普通澄清通过工作簿和普通回复提出，按用户规则把待决定的选项放在回复最后，再结束当前回合，让后续子线程通知能重新
唤醒管家。同步提问工具（如 `AskUserQuestion`）会挂起整个会话，使子线程通知只能排队，因此普通澄清不用这类工具。
真正要求暂停执行的授权或审批仍按原有规则等待；缺少答案的分支不擅自执行。

只有所有当前可推进的分支都依赖用户时，才报告整体等待；仍用普通回复结束回合，保留接收后续回报和求助的能力。

## 推进循环

1. 派发前先核实决定任务范围的事实（归属、现网或环境实况、用户原意），任务里写的是核实过的事实而不是推测；要大量阅读才能核实的，先按上文派只读调研线程。实现细节仍留给子线程，管家不在主会话预查具体代码行或代拉大段数据落盘。再按 `$bb-model-routing` 的任务模板与分档标准构造并派发下一步任务，“先读”包含工作簿路径。派发后按「收尾对账」结束回合，等 BB 通知。
2. 收到完成通知或阻塞求裁决通知后，只读通知摘要、子线程最终回复和它的 git 改动，不读子线程全文；强模型会话的上下文留给判断，不装子线程产物。结果是用户会直接碰到的（环境、配置、云资源、对外入口），先用只读命令核一次实况再验收、再报告。
3. 逐条处理“自行引入的决定”：进工作簿、接受但不记、退回重做三选一；通过 `bb-dispatch --record-decision <线程ID> --decision ...` 回写裁决（终态由脚本自动记录，有误时再加 `--outcome` 改正）。用户事后纠正的问题能追溯到某次派发时，把该线程改记为 `--decision reworked`（覆盖原裁决），让 `--history-summary` 的接受率反映转手丢掉的部分。
4. 阶段收口、路线状态变化、决策变更或新冒出用户待办时，更新工作簿，运行 `scripts/steward_workbook.py --mode should-commit --file <工作簿路径>` 通过且确认 `should_commit: true` 后提交。
5. 阶段完成后继续下一条可推进的路线；用户依赖按“等待用户时继续推进”处理。

## 收尾对账

每个回合结束前对一遍账：路线里每个未完成行落在下面一种状态，写在该行 `←` 之后。

- `进行中 thr_xxx`：有线程正在做这件事，行里写出它的线程 ID。
- `等用户`：有未完成的用户待办，"挡住"栏写着这一行的阶段编号（行没有编号时写标题）。
- `定时 MM-DD HH:MM <做什么>`：已经排定时间的动作，如 automation、提醒、窗口。
- `排在 <事项> 后：<依赖的产出>`：要消费前一项的产出，或和它写同一目标；前一项完成，这一行就该推进。

落不进这四种的行（包括"随后""暂缓""远景"）当场派出去；用户明确说先不做的，从路线删去、记进关键决策。
状态有变化就按「工作簿」提交，然后跑对账检查，退出码 0 再结束回合；退出码 2 时按输出逐项处理：

```bash
python3 scripts/steward_workbook.py --mode reconcile --live --file <工作簿路径>
```

`--live` 经 `bb thread list` 核对 `进行中` 的线程：在跑、有排队消息、有后台活动或结束不到 30 分钟算活着。

## 看门狗

`scripts/steward_watch.py` 由 BB 脚本 automation 每 30 分钟跑一次，不调模型：管家回合失败且没有排队的重试时
替它重试，恢复后提醒核对失败期间的通知；管家空闲而对账不过时，把问题行发给管家。节流和升级规则见脚本
`--help`。会话开始时登记，首次登记会在当前项目创建 automation：

```bash
python3 scripts/steward_watch.py register --workbook <工作簿路径> [--ref origin/<分支>] [--name <简称>]
```

工作簿以远端分支为准、主工作区不在该分支时传 `--ref`。收到 `[bb-steward 看门狗]` 消息就按「收尾对账」
处理，不用回复它。

## 回看

运行事实在 BB 线程记录与 `bb-dispatch` 本地账本里：`bb thread show <线程ID>` 看单次派发结果，`bb thread list` 看本会话派出的线程，`bb-dispatch --history-summary` 看难度分布、候选成功率/接受率、原会话重试与冷却走势和复盘提示，`scripts/steward_workbook.py --mode check --file <工作簿路径>` 检查工作簿健康度。工作簿不存线程 ID 以外的运行细节。

看门狗的记录在它自己的事件日志里：`scripts/steward_watch.py report --since <分钟>` 看各管家最近的检查、催办和需要用户看一眼的事，`scripts/steward_watch.py summary` 看 7 天内的催办后解决率、重试与失败次数和复盘提示。日志超过 2 MB 丢掉较早的一半，不做长期折算。
