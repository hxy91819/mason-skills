# 换机盘点方法

## 先分类证据

接手一台现有主机时，先给每条事实标来源，再决定哪些能写进代码：

| 分类 | 含义 | 例子 |
| --- | --- | --- |
| 仓库声明式 | 已跟踪、可重建 | Compose、Dockerfile、迁移、systemd 模板、Ansible role |
| 仓库手工命令/文字 | 文档写了步骤，但没有可执行入口 | “手工建库”“在主机上执行某脚本” |
| 主机独有 | 只在该主机查到，仓库没有具体记录 | 共用网关、证书配置、历史 hotfix、UFW 规则 |
| 私有文件 | 本机或主机的未跟踪配置 | `.env`、`private.env`、SSH 别名 |
| 未核实 | 当前证据无法确认 | 云安全组、DNS 控制权、历史发布来源 |

“主机独有”表示本次仓库/已知私有入口对照下没有找到，不表示已经搜索所有机器或私有存储。不要把缺项直接判成“只在人脑里”。

只做只读检查：文件元数据、受限配置读取、Docker 元数据、systemd 查询、防火墙查询、数据库 `SELECT`/`SHOW`。不执行部署、备份、迁移、恢复、服务重载、证书申请或真实模型请求，除非用户另行授权。

## 盘点清单

### 主机与访问

1. OS、架构、CPU/内存/磁盘；是否满足应用和数据库的最低要求。
2. SSH 地址、端口、账号、私钥、可信主机指纹；账号是否在 sudo/docker 组。
3. 云安全组、DNS、公网 IP/域名、入口端口；哪些在云控制台，哪些在主机 UFW。
4. 时区、时间同步、日志轮转、磁盘余量。

### 运行时

5. Docker Engine 版本、Compose 版本、是否开机启动。
6. 容器清单、镜像标签/digest、重启策略、资源限制、健康检查。
7. 网络（bridge/overlay/external）、端口绑定、卷/挂载、runtime 目录。
8. 应用、Worker、Web、数据库、Redis、网关的依赖顺序。
9. 反向代理/网关：进程、配置路径、证书、日志、站点块、上游端口。
10. 防火墙规则：默认策略、已放行端口、共享规则。

### 构建与发布

11. 镜像从哪来：本机构建、CI、镜像仓库、主机构建、手工 `docker save`。
12. Dockerfile 路径、构建参数、目标平台、是否可重现。
13. 镜像标签与 commit 的对应关系；有没有 digest。
14. 发布脚本/流水线是否存在；没有则记录手工命令。
15. 历史 hotfix、补丁目录、镜像 tar 归档；它们是否已回收进仓库。
16. 发布记录、验收记录、回滚记录。

### 配置与密钥

17. 私有 env 键名（不记录值）；哪些是应用必需、哪些有默认值。
18. 应用密钥/JWT 是否沿用；重新生成会影响哪些会话。
19. 外部 OAuth/模型/推送/邮件凭据；回调地址和 origin 是否匹配。
20. 数据库管理员密码、应用角色密码、连接上限；密码是否只在一处。
21. 配置里是否有硬编码 IP/域名/端口；换机后哪些必须改。

### 数据库

22. 实例类型/版本、容器名、网络、端口、数据卷。
23. 角色：是否超级用户、LOGIN、连接上限、search_path。
24. 库/schema/owner；迁移版本；扩展。
25. 连接预算：应用池 + Worker 池 + 管理连接，是否超过实例上限。
26. 备份：目录、脚本、timer、保留期、最近一次成功时间、是否验证过恢复。
27. 异地副本：是否存在、目标、频率、恢复演练。
28. 迁移历史：旧库到新库的 dump/restore 步骤、字符集、owner/privilege 处理。

### 应用与验收

29. 应用健康端点、Web 健康端点、静态 Manifest/Service Worker 路径。
30. 登录方式、账号角色、OAuth 回调、邀请/额度等运营数据。
31. 浏览器验收路径、视口、关键页面、已知问题。
32. 监控/告警、日志位置、磁盘清理、证书续期。

## 主机独有项

盘点的价值在于把“只在这台机器上”的东西列出来，决定是纳入代码、写进 runbook，还是明确接受为手工步骤。常见主机独有项：

- 共用网关的完整站点配置、证书账户、日志目录、服务 unit；
- 云安全组、DNS、负载均衡、对象存储；
- 历史 hotfix 目录、镜像归档、旧的私有配置副本；
- 数据库实例的实际角色/权限、连接上限、扩展；
- 备份产物和恢复演练记录；
- 监控/告警接入。

这些不一定都要自动化。至少要写清：谁负责、多久检查一次、换机时怎么恢复、没有它会失去什么。

## 需要人提供的最小输入

| 输入 | 为什么仓库无法提供 | 条件 |
| --- | --- | --- |
| 目标主机与管理访问：SSH、sudo/docker 权限、可信指纹、云网络权限 | 仓库不创建主机、不分发凭据 | 必须 |
| 对外 origin：IP/域名、HTTPS 端口、DNS 管理权限 | 关联证书、网关 Host/Origin、OAuth 回调 | 公网入口必须；域名/DNS 按选用 |
| 要部署的版本/镜像来源 | 现用镜像可能无法从某个 commit 重建 | 必须 |
| 数据库前提：复用还是新建；复用则管理员访问、实例/网络定位 | 仓库不能推导现有实例 | 复用必须；新建需创建权限 |
| 迁移连续性：空白还是保留旧数据；最终备份、切换窗口、是否沿用应用密钥 | 决定用户/会话/团队/额度能否延续 | 有旧数据时必须 |
| 应用必需密钥（模型、OAuth、推送、邮件等） | 只能私密注入 | 对应功能启用时必须 |
| 新用户/团队及私密交付渠道 | 仓库不知道实际接收人 | 仅新增时 |

如果要求整机丢失后也能恢复，还需要现机以外的可用数据副本。没有这个副本时，同机备份不能防整机故障。

## 输出

盘点结果写成一份可执行的清单，至少包含：

- 证据表：事实、来源分类、证据（路径/只读命令输出摘要）、是否已脱敏；
- 最小输入表：谁提供、何时必须、没有会阻塞什么；
- 主机独有项：保留位置、负责人、恢复方式；
- 未核实项：明确写“未核实”，不要用推测补齐；
- 迁移步骤：从新主机到可用环境的顺序，标注哪些步骤需要人工；
- 回退边界：旧栈材料在哪、怎么启动、哪些数据写入后不能直接回退。

报告里不要放真实密钥、完整私有 env、未脱敏的公网 IP 或主机名。需要引用时用占位符，并说明替换规则。
