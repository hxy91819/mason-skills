# 逐项改善移动端产品体验

读取移动端体验审计 HTML 报告和其中的真实截图，按照报告中的问题顺序挨个修改。每项修改都要同时确认手机体验和桌面端没有被破坏；桌面端允许因共享改动获得有意的设计优化。

## 固定复查基准

- 手机：iPhone 16，`393 × 852` CSS px；iPhone 17，`402 × 874` CSS px。
- 桌面：`1920 × 1080` CSS px。
- 修改前后使用相同路径、角色、数据、页面状态、滚动位置和浏览器缩放；截图必须来自真实浏览器。

## 大列表与查询

当列表可能持续增长，或一次渲染全部记录已经造成页面过长、滚动或性能问题时，优先让后端执行分页和搜索。移动端与桌面端共用同一套权限、资格判断、稳定排序和查询参数；前端只渲染当前页并处理加载、空结果和错误状态。不要只用收合、限高或 `overflow` 把完整数据藏起来。

每次处理一个问题：

1. 确认问题编号、进入路径、角色和修改前截图；在改代码前额外截取该页面的桌面基线（`1920 × 1080`）。
2. 针对这个问题完成修改，并进行相关行为验证。
3. 使用相同的路径、角色和页面状态，在两组手机视口中用真实浏览器复查：
   - iPhone 16：`393 × 852` CSS px
   - iPhone 17：`402 × 874` CSS px
4. 使用相同状态在 `1920 × 1080` 桌面视口复查，检查共享 HTML、CSS、导航、表格、按钮和滚动行为是否被破坏。不能用源码正则或单元测试替代这一项；桌面出现有意的设计优化可以接受。
5. 截取手机和桌面的修改后真实页面；确认桌面没有功能、信息层级、布局或交互破坏后，再继续下一个问题。若桌面有意优化，必须在报告中说明原因和范围，并与真正的回归区分开。

输出一份 HTML 对比报告。每个问题包含：

- 原问题和修改说明
- 手机修改前截图与修改后截图
- 桌面（`1920 × 1080`）修改前截图与修改后截图
- 使用的路径、角色、页面状态和视口
- 若涉及大列表，记录后端分页／搜索请求与当前页结果的可观察证据
- 验证结果（桌面无破坏；有意优化需单独标注）

前后截图的呈现组件与配对规则（滑块对比为默认，整页长截图并排）见 [references/report-format.md](references/report-format.md)。

用户没有指定保存位置时，暂时存放在本地。
