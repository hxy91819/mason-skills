## Local aggregate fork maintenance

This checkout is maintained as a non-maintainer fork. After setup/migration cutover, its root workspace stays on `local/aggregate` for integration and experience. Its release baseline is the selected tag and SHA in the frozen train; the upstream tracking ref discovers newer releases. Verify and package exact candidates in isolated worktrees. Publish completed snapshots to the personal fork; never use the aggregate for an upstream pull request.

Every product change starts on an independent first-tier `feature/*` or `fix/*` source in its own worktree. Its registered ordered commits, not its complete ancestry, define the patch. Related patches may enter a second-tier domain worktree that owns stable-release adaptation; dormant first-tier refs remain fixed until their feature changes. Small forks can start and remain direct-only. Add domains for recurring shared compatibility work. Each adaptation records its reason, affected feature IDs, and source mapping. Product behavior changes return to a first-tier source. Contributions select the target feature, its dependencies, and relevant adaptations.

`config/local-aggregate-features.json` is the authoritative registry for first-tier ownership, dependencies, domain mappings, last packaged commits, specification, actual upstream feedback, related context, and disposition. A committed train manifest freezes one stable tag and SHA, selected domain members, shared dependencies, direct patches, and verification inputs. Build credentials created after the source snapshot bind its SHA and train digest to the real package artifacts and toolchain. Keep the human overview generated from or linked to these records instead of duplicating moving SHAs.

Invoke `$autoreview` after development and relevant domain/candidate verification; a source is verified only after no accepted/actionable findings remain. Publish completed source and domain branches, contribution exercises retained for evidence, immutable train refs, and the completed aggregate to the personal fork. Rebased or rebuilt moving refs may use explicit-lease `--force-with-lease` pushes without a separate approval prompt; immutable refs are create-only and upstream is never force-pushed. The aggregate is composed from the frozen train, not old aggregate ancestry. Repair product conflicts in the owning source or domain worktree.

Fork issues are local specifications; related issues are context, and only `upstreamFeedback` records an actual upstream report. Use `needs-feedback` for missing reports and `internal` for local maintenance instead of requiring an unrelated issue. Opening an upstream issue retains the explicit confirmation boundary in the skill.

Use `$open-source-fork-maintenance` for new-project setup, old-fork migration, upstream synchronization, domain/aggregate rebuilding, or packaging. It audits sources, domains, releases, and feedback, then continues the authorized path without repeated approval. Existing forks migrate on their current baseline before upgrading it. Include required maintenance assets in the train and prove full-tree reconstruction. Once the maintenance path is chosen, aggregate root replacement and personal-fork publication require no further approval. Deployment follows this project's existing workflow and authorization; migration or source publication alone does not deploy a service.

Upgrade to the latest tag matching the project's release channel by default. Unreleased trunk commits remain debt unless the user chooses them. An explicitly deferred upgrade can package verified changes on the current baseline while reporting that debt. Build commands, supported schema/protocol upgrade paths, and runtime/deployment details belong to project guidance, not this shared model. Report verified, packaged, published, and deployed states separately.
