# 实测证据：十几个线程并行时的瓶颈（2026-11-05）

SKILL.md 清单里每条"为什么"的出处。对象是一个四人团队带十几个 Agent 并行开发的平台项目；数字取自 BB 线程账本、代码托管平台的 MR 记录、master 历史、子线程复盘与管家观测脚本，时间为北京时间。只在需要向用户出示依据、或判断自己项目是否同病时读。

## 规模

- 一个仓库，BB 线程 421 个，其中 389 个由两位管家线程派出；高峰 14 个线程同时活跃。
- 11-04 合入 138 个 MR，11-05 合入 123 个；下午到晚上每小时 10–16 个合入，master 每 4–6 分钟前进一次。
- 合入构成：发布 MR 约 35%，管家工作簿 MR 15–25%，真正的工作 MR 每天 80–100 个。

## 合入通道

| 指标 | 11-04 | 11-05 |
| --- | --- | --- |
| 工作 MR 从建到合入 p50 / p90（分钟） | 15 / 77 | 41 / 106 |
| 全量 MR CI 墙钟 p50（分钟） | 14 | 14 |
| 纯文档 MR 墙钟 p50（分钟，走全量） | 13.75 | 13.75 |
| 关闭未合入的工作 MR | 21%（230 个里 48 个） | |
| 一条分支开出的 MR 数（最多） | 18 | |

- 合入工具遇 master 漂移就重跑，最多两轮；每轮 14 分钟，几乎每个 MR 都要两三轮，"整个过程可能接近一小时"写进了文档。
- 195 次 MR 构建里 63 次取消，47 次是同 SHA 的 close/reopen 顶掉正在跑的构建（托管平台的 MR 快照陈旧，线程用 close/reopen 刷新），共耗 145 分钟。
- 自有检查池一个节点、并发 4，高峰 12 个构建同时跑，containers 作业排队 30 分钟以上；机器 16 核 load 4–8，机器没满，是并发上限卡住。当天 15:26 把并发提到 6（CI 平台的节点设置，心跳生效，不用重启）。
- 合入后的主干全量检查 cancel-in-progress: true：当天约 60 次运行，34 成功、19 被后来的合入取消、6 失败；15:04–16:24 的 80 分钟没有一次成功。容器类检查移到合入后之后，它成了唯一覆盖，必须改成"跑完再说，排队只跑最新"。
- 一个线程启用运维应用时改坏了发布夹具，主干变红，所有在途 MR 的重跑一起失败，关键路径的 MR 被拖了几个小时。

## 共享测试环境

- 合入即发布：发布滞后 p50 3 分钟、p90 95 分钟、最大 141 分钟；镜像构建排队中位 12–45 分钟。
- 一天两次发布被非核心组件卡死：运维应用连不上库 CrashLoop 导致 Argo Degraded，后面波次的核心应用不更新；金丝雀副本的渲染误继承同节点约束。用户等着截图的两个修复因此上不了环境。
- 关键路径阶段（环境上首条真实实例链路）后面排着至少 9 个阶段，它的延误全部来自 CI 排队和他人的回归。

## 管家枢纽

- 环境管家一个会话挂 64 个子线程；两位管家上下文用到 87–89%（435k/444k of 500k）；一个跑了 20 小时的 Codex 子线程会话 45MB 后 turn/start 超时，再也接不了消息。
- 工作簿单文件 56KB、161 个阶段，每次更新一个 MR，5 天 68 个工作簿 MR，37 次"merge master 解冲突"多数落在这类共享文件上。
- 管家大量回合花在：查 CI 排队、找停摆 MR 的归属、研究怎么提执行机并发。

## 会话与等待

- BB 空闲 30 分钟回收 provider 会话，会话里的后台进程随之被杀：CI 绿了的合入进程没人合（一小时），验收链被截断。根治是把长等待放进 `bb terminal`（持久终端）并在结束时 `bb thread tell` 自己。

## 本机

- 开发机 32 核 62G，14 个活跃线程时 load 26–28；80 个 worktree；Go 缓存 42G。
- 本地 `make check` 3–9 分钟；复盘里一个任务跑 4 次全量检查很常见，其中 2 次是环境问题：同一 worktree 重叠跑 check 时 `npm ci` 竞争；golangci-lint 跨 worktree 进程锁；共享 venv 带着已删 worktree 的绝对 shebang；嵌套 make 继承 MAKEFLAGS 覆盖夹具。
- 一次 cat 五份文档 24k token 被截断，Agent 又用 rg/sed 补读。

## 不是瓶颈的

- 审查返工：派发账本 1783 次，验收率 93–96%。独立审查每个任务抓出 4–7 个 P1 是系统在起作用；但每个 P1 修复都是一轮 CI，所以它放大了合入通道的问题。

## 当天拍板的改法

一次绿灯即合入；合入前只留公共池约 5 分钟静态检查，容器类检查移到合入后（改迁移、镜像、部署输入时才在合入前跑）；发布不等主干检查；纯文档 MR 只跑链接检查；工作簿移出仓库到 `.local/steward/`；非核心组件独立 Argo Application，测试与生产同一渲染器；派发并发按 provider 上限节流；本机 check-fast 与全局并发槽位。否决：按管家上下文用量强制交接；先加第二台 CI 机器（等前面落地后看排队再定）。
